全体の関係

保存の階層もこの入れ子のとおり（workspaces/{ws}/papers/{p}/blocks/{b}、…/papers/{p}/versions/{n}、workspaces/{ws}/search/{…}。全体は保存先の配置）。ワークスペースそのものは設定にあり、保存先には ID の名前空間としてだけ現れる。ユーザー・トークン・セッションはワークスペースの外にある。

ID

ID は papers が発行し、外部のサービスの ID（Google の subject など）をそのまま使わない。一度決めた ID は変えず、削除後も使い回さない。

対象形式発行例
ワークスペース小文字・数字・ハイフンの短い名前（^[a-z0-9]+(-[a-z0-9]+)*$、63 文字まで）設定ファイルに書くsecurity
すべて（ペーパー・ブロック・添付・ユーザー・セッション・トークン）UUID v4（ランダム 122 ビット）を英数字だけの base62（0-9 A-Z a-z）にした 22 文字。短いときは先頭を 0 で埋めて長さを揃えるサーバー1csQdaLtbzOEz6NzfMfH6Z
版ペーパーごとの通し番号（1, 2, 3 …）サーバー（保存のトランザクション内）…/papers/{id}/versions/2
ブロックの更新番号（Rev）ブロックごとの内部の番号。内容が変わるたびに 1 増えるサーバー画面には出さない
検索エントリ{ペーパー ID}_{ブロック ID}、タイトルは {ペーパー ID}_titleサーバー（派生）
セッション・トークンの秘密上の 22 文字の ID + 別のランダムな秘密（保存するのは秘密のハッシュだけ）。トークンは pap_{ID}.{秘密} の形で渡すサーバー
  • 形式は 1 つ: ID はすべて UUID v4 を短くしたもの。並びが要るものは作成時刻や番号（版）で持つ。
  • v4 を短くする理由: URL・API の応答・AI に渡す本文に何度も出るので、36 文字から 22 文字に縮める。記号を含まないので、ダブルクリックで全体を選べ、区切り文字とも紛れない。大文字と小文字を区別する。ランダムなので推測されず、時刻も漏れない。
  • 受け取るときの検査: 英数字 22 文字で、復元すると UUID v4 になることを確かめる。形式が違えば、存在しない ID と同じく 404 にする。
  • ID はすべてサーバーが発行する: クライアントが ID を決めると、他のペーパーや削除済みのブロックと同じ ID を送られたときの扱い（履歴が混ざる、削除済みのブロックを別物で上書きする）を全部の入口で防ぐ必要があり、AI や API からの書き込みでは信用できない。クライアントが決められる ID はない。
  • 同じ操作のまとまりの中で新しいブロックを指す: insert には仮の名前（ref、例 "n1"）を付けられ、後の操作は after: "ref:n1" のようにそれを指せる。仮の名前はそのまとまりの中だけで有効で、保存されない。応答は仮の名前と発行した ID の対応を返す。
  • 画面に先に出す: 画面は新しいブロックを手元の仮のキーで先に表示し、応答で本当の ID に置き換える。置き換える前の編集は手元に溜め、ID が分かってから送る。同時に流れてくるライブの変更は本当の ID で届くので、自分の操作の応答と突き合わせて二重に表示しない。
  • ID と Firestore: ID はランダムなので、Firestore で単調に増える ID の書き込みが一か所に集中する問題は起きない。
  • URL: ペーパーの今の状態は /ws/{ワークスペース}/p/{ペーパー ID}、最新の版は …/latest、版 vN は …/v/{番号}（今の状態と版）。ワークスペースが読める名前なので、URL の前半は読める。

ワークスペース

ペーパーの入れ物で、権限の基本単位。「チーム」や「部署」くらいの粒度を想定する。ワークスペースは設定ファイルで定義し、画面や API からは作らない・変えない（hecatoncheires と同じ方式）。ワークスペースをまたぐ操作（移動・横断検索）はない。

定義の仕方

# --config に渡したディレクトリの中の 1 ファイル = 1 ワークスペース
# workspaces/security.toml
[workspace]
id          = "security"            # 変えない。保存先の名前空間になる
name        = "Security Team"
description = """
障害対応の手順と、インシデントの振り返りを集める。
手順は番号付きリストで書き、コマンドはコードブロックにする。
"""                                   # AI にこのワークスペースの決まりごととして渡す
emoji       = "🛡️"
language    = "ja"                  # 任意

[authz]                              # 誰がこのワークスペースを使えるか（allow を返す）
policy = ["policies/security.rego"]
id
^[a-z0-9]+(-[a-z0-9]+)*$、63 文字まで、全ワークスペースで一意。変えてはいけない（保存先のパス workspaces/{id}/… になる）。名前を変えたいときは name を変える。
name
表示名。省略すると id。
description
何を集めるワークスペースか、どう書くか。人には説明として見せ、AI には MCP の papers_guide と読み書きの結果に「このワークスペースの決まりごと」として渡す。
emoji / color
画面の目印。どちらか一方。
language
AI に書かせる言語の既定（任意）。
authz
このワークスペースを使える人の規則。Rego が allow（真 / 偽）を返す（アクセス）。
  • 管理者の権限で決めることは、すべて設定ファイルに書く。設定ファイルはデプロイと一緒に届くもので、変えられるかはデプロイの権限で決まる。画面と API には、全体に関わる設定を変える入口がない。
  • 起動時にすべて検証し、1 つでも不正なら起動しない。変更は再起動で反映する。
  • ワークスペースの表示上のまとまり（サイドバーでの分類）は全体設定ファイル（--global-config）に書く。まとまりは表示の整理だけで、権限には効かない。
  • ホーム: 起動時に、設定の各ワークスペースについてホームのペーパーがなければ作る（何度起動しても 1 つ）。どれがホームかは保存先の workspaces/{id} の記録の HomePaperID で持つ。最初のタイトルは name。/ws/{id} はホームを開く（木）。
  • description は「AI への決まりごと」（デプロイで変える）、ホームの本文は「人と AI が読むワークスペースのまとめと入口」（誰でも書ける）。
  • 設定から消したワークスペースのデータは、ホームも含めて消えない（D13）。

これにより、画面と API からワークスペースを作る・名前や使える人を変える機能はなくなる。作成の許可設定も不要になる。ワークスペースの削除・アーカイブは「設定から外す」で表す（D4 からは外す）。

ペーパー

タイトルとブロックの並び。人も AI も同じペーパーを同じ操作で書く。書いたものはすぐ今の状態（編集中の最新版）になる。誰か（人か AI）が明示的に保存したときだけ版ができ、履歴はその版の列で表す。

ID / WorkspaceID
不変。ワークスペースをまたぐ「移動」は、新しい ID での写しと元の削除として行う（木）。
ParentID
親のペーパー。親の本文にある自分のペーパーブロックと常に一致する（同じトランザクションで書く）。ホームと private のペーパーは空。祖先の列は持たない（木）。
Title
1 行、256 バイトまで。空でもよい（画面では「無題」）。版に含まれるが、独立した番号は持たず、同時に変えたら後勝ち（D1）。
Visibility
public（既定）か private。意味はアクセス。変えられるのは作成者だけ。private のペーパーは木に入らず、作成者だけの平らな一覧に置く。
VersionNumber
最新の版の番号。0 なら下書き、1 以上なら正本。
ArchivedAt
アーカイブした時刻。空でなければアーカイブ（版の有無によらない）。一覧・検索は既定でアーカイブを除く。
DeletedAt / DeletedWith
ゴミ箱に入れた時刻と、配下ごとの削除を始めたペーパーの ID（D4）。30 日後に本当に消す。
CreatedBy
作成した書き手。private のペーパーを読み書きできるのは、このユーザー（AI が作ったなら代理元のユーザー）だけ。
UpdatedAt / UpdatedBy
おおよその最終更新。ペーパー本体への書き込みを減らすため、タイトル変更か、前回から 1 分以上たった書き込みのときだけ更新する。最大 1 分遅れる（D6）。

ペーパーの状態

なぜペーパー本体をほとんど書かないか

Firestore は 1 つのドキュメントに毎秒 1 回程度しか書けない。全員の書き込みがペーパー本体を書くと、そこが詰まる。だから中身はブロック側に持ち、ペーパー本体はタイトル・親・公開範囲・状態・おおよその更新時刻だけにした。親・公開範囲・状態はまれにしか変わらない。

木（ペーパーの入れ子）

入れ物の概念（フォルダ）は作らない。子ペーパーは、親の本文の中のペーパーブロックとして置かれる（Notion と同じ形）。親の本文がそのまま、子を紹介しながらまとめる場所になる。人が「どこに何があるか」をつかむための構造で、深さは制限しない。詳しい検討はペーパーの整理。

形

  • ワークスペースごとにホームのペーパーが 1 つある。ホームは消せず、動かせず、private にできない。
  • ホーム以外の public のペーパーは、ちょうど 1 つの親の本文に、ちょうど 1 つのペーパーブロックとして置かれる。いちばん上の段はホームの本文にある。
  • private のペーパーは木に入らない。親も子も持たず、作成者だけの平らな一覧に置く。public にすることは、どこかの親に置くこと。private にできるのは子のない public のペーパーだけ。
  • 子の並び順は、親の本文のペーパーブロックの並びそのもの。別には持たない。
  • 深さは制限しない。実装の安全弁として、親を辿るのは 100 段で打ち切る。

操作ごとに起きること

操作起きること
子を作る親の本文に paper ブロックを挿入し、同じ操作のまとまりで子のペーパーを作る。
ペーパーブロックを消す子の作成者本人なら、子を配下ごとゴミ箱に入れる。本人でなければブロックは消さず、子を配下ごとアーカイブする（D18）。ゴミ箱へは（配下に DeletedAt と DeletedWith）。画面は消す前に件数を見せて確かめる。親を版に戻してブロックが戻れば、同じ DeletedWith の配下も戻る（作成者本人のとき）。
移動（同じワークスペース）元の親の本文からペーパーブロックを消し、新しい親の本文に新しいペーパーブロックを足し、子の ParentID を書き換える。この 3 件だけを 1 つのトランザクションで書く。配下には何も書かない（配下は親を指しているだけなので付いていく）。移動は後勝ちで、衝突の対象にしない。移動そのものの記録は残さない。親の本文の変化は、次にその親の版を保存したときに版に表れる。
移動（ワークスペースをまたぐ）新しい ID で配下ごと写し、元を配下ごとゴミ箱へ入れ、元の ID から新しい場所への転送の記録を残す。今の状態と最新の版（写しの v1 になる）を写し、古い版は写さない。
親を版に戻すよそへ移った子のペーパーブロックは戻さない（移動した時点で元の親の管理から外れている）。結果に「戻さなかった子」を添える。ゴミ箱にある子は、戻す人がその子の作成者本人なら戻る（本人でなければ戻さず、結果に添える）。

読み方

  • ペーパーは親だけを持ち、祖先の列は持たない。移動で数千〜数万のペーパーが動いても、書くのは 3 件で済むため。
  • パンくず・パス（security / 手順 / DB 切り替え）と循環の検査は親を辿る。サーバーは「ペーパー → 親」の対応を手元に覚え、変更フィードで更新する。トランザクションの中では読み直して確かめる。
  • 子の一覧は親の本文から分かる。子のタイトル・状態は一括取得で 1 回読む。
  • 「この配下で探す」は、検索の当たりそれぞれの親を辿って絞る。「配下をまとめてアーカイブ・書き出す」は子の索引で 1 段ずつ降りる裏の処理。
  • AI はパスで親を指定できる（同じタイトルが複数あれば候補を返す）。URL は ID のまま。

サイドバー

木全体は出さない。ホーム、ユーザーごとのお気に入り（Pin: ユーザー・ワークスペース・ペーパー・並び順キー）とその配下（開いた段だけ読む）、最近開いたペーパー数件、自分の private の一覧を出す。

ブロック

編集・衝突・検索エントリの最小単位。ブロックは内容（種類・本文・属性）と位置（親・並び順キー）を持ち、この 2 つを分けて扱う。

ID
サーバーが発行する 22 文字の ID（ID）。クライアントは決められない。一度使った ID は、削除後も同じブロックのものとして扱う（復元で戻る）。
Type
種類。下の表のどれか。
Content
本文。意味は種類ごとに違う（下の表）。256 KiB まで。
Props
種類ごとの属性。その種類に関係ない属性は保存前に消す（種類を変えても古い属性が残らない）。
ParentID
親ブロック。表のセルだけが親（表）を持つ。それ以外は空（ペーパー直下）。木は 1 段だけ。
Order
兄弟の間の並び順キー（分数インデックス）。2 つのキーの間には必ず別のキーが作れるので、挿入や移動で他のブロックを書き換えない。同じキーになったら ID の順。
Rev
内部の更新番号。内容（種類・本文・属性）が変わるたびに 1 増える（位置の変更では増えない）。書き手はこれを「元のリビジョン」として送る。画面には出さない。
CreatedBy / UpdatedBy
最初の書き手と、最後に変えた書き手（時刻つき）。

ブロックの一生

今の状態と版

ペーパーにあるのは 2 つだけ。今の状態（編集中の最新版。人と AI の書き込みがすぐ反映される）と、版（人か AI が明示的に保存した、ペーパー全体の不変の写し）。自動保存という概念はなく、編集の細かい履歴も残さない。履歴の参照と復元は版の単位で、ペーパー単位で行う（ブロックごとには行わない）。

版が持つもの

PaperID + Number
ペーパーごとに 1 から欠番なし（v1, v2 …）。保存のトランザクションで Paper.VersionNumber と一緒に決める。
Title
その時点のタイトル。
Blocks
その時点の全ブロックの (ブロック ID, Rev, 親, 位置) の列。中身は BlockSnapshot（ブロック ID + Rev ごとの不変の写し）を指す。保存のとき、前の版から Rev が変わったブロックだけ写しを作り、変わっていないブロックは前の写しを指す。ペーパーブロックは子の ID を含むが、子の中身は含まない（子はそれぞれの版を持つ）。
Note
この版で何が変わったか（任意。AI に下書きさせてもよい）。
CreatedBy / CreatedAt
保存した書き手（人か AI か、AI なら誰の代理か）と時刻。
  • 誰が保存するか: そのペーパーを使える書き手なら誰でも（人も AI も）。画面の「保存」、API・MCP の save_version。システムが自動で保存することはない（自動保存という概念はない）。誰が保存したかは版の一覧に出す（「v4 · Claude（Alice の代理）」）。
  • 最初の版（v1）で下書きから正本になる。正本から下書きには戻らない。要らなくなったらアーカイブする。
  • 取り消さない: 版は書き換えも削除もしない（ペーパーを完全に消すときだけ一緒に消す）。気に入らなければ前の版に戻して、新しい版として保存する。
  • 前の版と変わっていなければ保存しない（何も起きなかった、が答え）。

操作

書き手は操作（Op）の列を 1 回のリクエスト（操作のまとまり）で送る。全部適用されるか、何も適用されないかのどちらか。適用した結果が今の状態になる。まとまり自体は記録として残らない。

insert種類（位置は after、仮の名前 ref は任意）。paper なら子のタイトル不要ブロックの追加（表ならセルも、paper なら子のペーパーも）—
updateブロック必須内容の更新（Rev +1。表の形が変わればセルの追加・削除も）内容が変わらない

moveブロック（位置は after）不要位置の変更位置が変わらない、または削除済み
set_titleタイトルなし（後勝ち、D1）タイトルの変更タイトルが同じ

操作のまとまりの約束

  • 応答は結果と、insert の仮の名前と発行した ID の対応を返す。
  • 1 回で変えられるブロックは 240 まで、書く本文の合計は 3 MiB まで。超えたら分けてもらう。
  • 複数のペーパーにまたがる操作（移動・公開範囲の変更）も 1 つのトランザクションで書く。
  • メッセージは持たない（説明は版のメモに書く）。

人の画面はブロックから離れるたびに送るが、それは今の状態を書き換えるだけで、版は増えない。

元のリビジョンと衝突

ロックは持たない。書き手が「どの状態を見て書いたか」（そのブロックの Rev = 元のリビジョン）を添え、その後に他の書き手が内容を変えていたら、気づかないまま消さないように一度止める。決めた経緯は同時編集の設計にある。

判定の規則

操作がブロック b を元のリビジョン r で書き換えようとしたとき、b のこのまとまりが始まる前の状態を cur とする。

状況結果
r がない、または r > cur.Rev不正な要求（400）
r = cur.Revそのまま適用
r < cur.Rev衝突。強行なら上書きする。Rev は内容が変わったときだけ増えるので、位置だけ動かされた場合は衝突にならない
b が他の書き手に削除されていた更新は衝突（強行でも。書き手は新しいブロックとして足し直す）。削除・移動は何もしない
b がこのまとまりの中で作られた判定しない
  • まとまりの中に衝突が 1 つでもあれば、何も書かずに全部を返す（409、衝突ごとに cur を添える）。書き手は全体を見て直せる。
  • 「このまとまりが始まる前の状態」と比べるので、同じまとまりの中で同じブロックを 2 回触っても、自分の 1 回目とは衝突しない。
  • 人の画面は編集を始めた時点の Rev を送る。保存直前に受け取った最新を送ると、編集中に届いた他人の変更を見逃す。
  • 強行で上書きされた内容は、版に入っていなければ残らない（細かい履歴は持たないため）。画面は強行の前に、上書きされる相手の内容を見せる。

衝突しないもの（意図して）

  • 位置: 並び替えは後勝ち。並びが入れ替わっても内容は失われない。
  • タイトル: 後勝ち。負けた側の変更も履歴に残る（D1）。
  • 行・列の削除で消えるセル: 元のリビジョンは見ない。編集中の人がいれば消す人に伝える（D3）。
  • 公開範囲: 作成者だけが変えるもので、同時に変える場面はない。後勝ち。

書き手と主体

似た言葉が 2 つあるので分けておく。主体は「いまリクエストしている者」、書き手は「その者が書いた、という記録」。主体でアクセスを判定し、主体が書けば書き手が残る。

主体（Principal）書き手（Actor）
ひと言でいまリクエストしている者書いた者の記録
いつリクエストごとに作る。保存しない書き込みのたびに作り、ブロック（作成者・最終更新者）と版（保存した人）に残す
中身ユーザー、使ったトークン人か AI か、代理元のユーザー、その時点の表示名、AI の名前、トークン
用途アクセスの判定（ワークスペースの規則、private の作成者か、トークンの制限）「誰が書いたか」の表示と、上書きされた人の特定
例トークン「Claude」で来た Alice「Claude（Alice の代理）」

入り方書き手の種類表示

  • ユーザーは papers が発行する ID を持ち、Google などの外部の ID とは Identity で結びつける。1 人が複数の外部 ID でログインできる。

アクセス

ロールは持たない。決めるのは 2 つだけ: ワークスペースを使えるか（設定の規則）と、ペーパーが public か private か。閲覧者・編集者・所有者の区別も、ペーパーごとの割り当てもない。

決まり方

  1. ワークスペースを使えるか: ワークスペースの設定の [authz] の Rego が allow を返すか（hecatoncheires と同じ）。入力はワークスペースとユーザー（ID・メール）。ユーザーのグループは当面持たない（D14）ので、規則はメールやドメインで書く。規則がないワークスペースの扱いは D12。
  2. ペーパーを使えるか:
    • public → ワークスペースを使える人なら読み書きできる（ホームを含む）
    • private → ワークスペースを使え、かつ作成者のユーザーであるときだけ読み書きできる
  3. トークンで狭める: 読み取り用のトークンでは書けない。許可したワークスペースの外は使えない。トークンは本人ができることを広げない。

判定結果はインスタンスごとに短時間（hecatoncheires と同じ 60 秒）キャッシュし、判定できないときは拒否する。

システム管理者はいない

papers の中に、規則や公開範囲を越えて何でもできる人はいない。管理者の権限で決めることはすべて設定ファイルに入れ、設定ファイルはデプロイと一緒に届く。

  • ユーザーの停止は、ログインの入口（Google のアカウント）か規則で行う。papers の画面にユーザー管理はない。
  • 作成者がいなくなった private のペーパーは誰も開けない（D18）。

使えない相手には「存在しない」（404）を返し、ペーパーやワークスペースがあることを漏らさない。読めるが書けない（読み取り用トークン）ときだけ 403 を返す。

保存先の配置

Firestore の文書の置き場所。木の形はモデルの「持つ」関係をそのまま映す。ペーパーの木（親子）はパスにせず、ParentID の値で持つ（移動でパスを変えないため）。

派生データ

検索エントリ

  • タイトル 1 つと、平文を持つブロック 1 つごとに 1 件。ワークスペースごとに置く（検索の範囲をパスで切るため）。
  • ブロックと同じトランザクションで書く。書いた時点で検索にも当たる。
  • 正本ではない。すべてペーパーとブロックから作り直せる。
  • アクセスの情報も木の情報（親・祖先）も持たない。検索の後で、ペーパーの公開範囲・ゴミ箱・アーカイブで絞り、「この配下で」なら当たりの親を辿って絞る。移動しても書き直さない。

変更フィード

  • ブロックの更新・削除、ペーパーの更新（親・公開範囲・状態の変化を含む）・削除を、変更後の状態として届ける。各ブロックの Rev と更新時刻を比べて新しいほうを反映すれば、何度届いても、順番が入れ替わっても同じ結果になる。
  • 取りこぼしは許す設計。接続し直したら必ず読み直す。受け手が遅れたら切って読み直させる。
  • 届けるために、ペーパーごとの短命の変更の記録（Event、例: 1 日で消える）を書き込みと同じトランザクションで書き、画面はそれを購読する（D17）。これは配信のためだけのもので、履歴ではない。

親の対応表

  • 各インスタンスが手元に持つ「ペーパー → 親」の対応。パンくず・パス・循環の検査に使う。変更フィードで更新し、ずれていても親（ParentID）が正本なので、書き込みのトランザクションでは読み直す。

不変条件

どの書き方をしても、保存されたデータが常に満たすこと。保存先の契約テストと use case のテストで守る。

  1. ペーパーはどれも、設定に定義されたワークスペースに属する（設定から消えたワークスペースのペーパーは、どの主体からも見えない）。
  2. private のペーパーは、作成者のユーザー（AI が作ったなら代理元）以外のどの主体からも見えない。検索・一覧・変更フィードも含む。
  3. ブロックはちょうど 1 つのペーパーに属し、ペーパーはちょうど 1 つのワークスペースに属する。ブロックはペーパーをまたいで動かず、ペーパーはワークスペースをまたいで動かない（またぐ「移動」は写しと削除）。
  4. 親を持つのは表のセルだけで、その親は同じペーパーの表。表のセルは、親の表の行 ID と列 ID の組ごとにちょうど 1 つあり、表にない行・列を指すセルはない。
  5. ブロックの属性には、その種類に関係する値しか入っていない。区切り線と表の本文は空。
  6. 各ブロックの Rev は 1 から始まり、内容が変わるたびにちょうど 1 増える。位置の変更では増えない。
  7. 操作のまとまりは、全部の結果が書かれるか、1 つも書かれないかのどちらか。ブロック・ペーパー・検索エントリ・変更の記録（Event）は同じトランザクションで書かれる。
  8. 強行しない限り、読んだ後に他の書き手が変えた内容が、知らないうちに消えることはない。
  9. 版の番号はペーパーごとに 1 から欠番なしで、どれも不変。版が指すブロックの写し（ブロック ID + Rev）は存在し、不変。Paper.VersionNumber は最大の番号と一致する。
  10. 版は書き手の明示的な保存の操作でだけ作られる。システムが自動で作ることはない。
  11. ID はすべてサーバーが発行したもので、クライアントが送った ID で新しいものが作られることはない。
  12. すべての変更には書き手があり、AI の書き手には必ず代理元のユーザーがある。
  13. 検索エントリは、タイトルと平文を持つブロックにちょうど 1 件ずつあり、内容が一致する。
  14. ペーパーの更新時刻は、最後の書き込みの時刻より最大 1 分（設定値）までしか遅れない。
  15. 設定の各ワークスペースには、ホームのペーパーがちょうど 1 つある。ホームは親を持たず、ゴミ箱にも入らず、public である。
  16. ホーム以外の public でゴミ箱にないペーパーは、ちょうど 1 つの親を持ち、親の本文にそのペーパーを指すペーパーブロックがちょうど 1 つある。逆に、ゴミ箱にない paper ブロックはどれも、その ParentID がそのブロックのペーパーである子を指す。
  17. 親を辿るとホームに着く（循環しない）。親は同じワークスペースの public のペーパー。
  18. private のペーパーは親を持たず、どの本文にもペーパーブロックとして置かれない。子も持たない。
  19. paper ブロックは本文の一番上の段にだけあり、表のセルにはない。
  20. 画像ブロックが指す添付は、そのブロックと同じペーパーに属する。添付の中身は変わらない。
  21. ゴミ箱に入ったペーパーの配下は、すべて同じかそれより前の削除でゴミ箱にある（ゴミ箱にない親の下に、ゴミ箱のペーパーのペーパーブロックが生きて残ることはない）。

決めること

モデルを詰める中で見つかった、曖昧さや穴と、その決定。青い線は決定済み、橙の線はまだ決めていないもの（いまはなし）。灰色の線は取り下げたもの。決定は実装の指示があるまでコードには入れない。

D1. タイトルは履歴の管理下に置くが、独立した番号は持たない（決定）

タイトルは版で追えるようにするが、ブロックのような独自の版番号や衝突の判定は持たせない。

  • 履歴: 版はその時点のタイトルを持つ。版同士の差分にもタイトルが出る。
  • 戻す: 版に戻せばタイトルもその版のものに戻る。
  • 持たないもの: TitleVersion のような独立した番号、set_title の元のリビジョン、タイトルの衝突。同時に変えたら後勝ち。

D2. 表の行・列に ID を持たせる（決定: B）

いまセルは「行番号・列番号」で場所を持つ。そのため、途中に行を挿入できない（後ろのセル全部の番号を書き換えることになり、全部のセルが変わって衝突も起きる）。また、行や列を縮めると、そこにあるセルが確認なしに消える。

案内容良い点気になる点
A. 今のまま（番号）行・列の追加・削除は末尾だけ単純途中への挿入・並び替えができない。縮めると確認なしに消える
B. 行・列の ID表の属性に行・列の (ID, 並び順キー) の列。セルは (行 ID, 列 ID)。行・列の挿入・削除・並び替えを専用の操作にする途中への挿入や並び替えで既存のセルが変わらない。削除するセルが明確になる表の属性が大きくなる（行 100 × 列 20 なら 120 個の ID）。操作が増える
決定: B。表は AI がよく書き、人が直す代表的な場面。行の挿入ができない表は使いにくく、番号のずれは衝突と大量の変更を生む。
  • 行・列の ID はサーバーが発行する（他の ID と同じ 22 文字）。同じ操作のまとまりの中で新しい行・列を指すときは、ブロックと同じく仮の名前 ref を使う。
  • 表の属性 rows / cols は (ID, 並び順キー) の列。表示順は並び順キーの順。
  • セルの属性は row_id / col_id。行・列を挿入・並び替えても既存のセルは変わらない。
  • 操作: 行・列の挿入（新しい行・列のセルも作る）、削除（その行・列のセルも消す。消すセルの扱いは D3）、並び替え（表の属性の更新だけ）。
  • 表もセルも普通のブロックなので、ペーパーを版に戻せば一緒に戻る。

D3. 行・列を消すとき、セルの元のリビジョンは見ない。編集中の人がいれば伝える（決定）

行・列の削除は一瞬の操作で、消したセルの中身は、版に入っていれば版に残る。だから消すセルの元のリビジョンを添えさせて衝突にする仕組みは入れない。代わりに、いまそのセルを編集している人がいれば、消す人にそれを伝える。

  • 消す人の画面: 消そうとする行・列のセルを誰かが編集中なら、「Alice が編集中です」と出してから消すかどうかを選んでもらう。編集中の人がいなければ確認なしに消す。
  • 編集していた人の画面: 自分のセルが消えたら「Bob が行を削除しました」と出し、書きかけの文字は手元に残してコピーできるようにする。保存しようとすると「削除済み」で拒否される。
  • API・AI: 編集中の人がいても消せる。結果に「編集中だった人」を返す。

新しく要るもの: 編集中の印（presence）。誰がどのブロックを編集しているかを、画面がサーバーへ知らせる（編集を始めた・やめた、数十秒ごとの更新）。サーバーは保存せず手元に短時間だけ持ち、変更フィードで同じペーパーを開いている画面に流す。今の変更フィードはサーバーから画面への一方向なので、画面からの知らせは HTTP で送る。表だけでなく、他のブロックでも「誰がどこを編集中か」の表示に使える。

D4. ペーパーの削除はゴミ箱に入れる（決定）

子ペーパーを消すと配下ごとゴミ箱に入り、戻すときも一緒に戻る、と決めた（ペーパーの整理 D21）ので、A に決まった。

  • DeletedAt と DeletedWith（削除を始めたペーパー）を配下の各ペーパーに付けて隠す。戻すときは同じ DeletedWith のものだけ戻す。30 日後に、DeletedWith ごとにブロック・版・写しまで本当に消す。
  • 検索エントリは消さず、検索の後で除く（大きな配下で一斉に書き直さないため）。
  • 親がゴミ箱にあるまま子だけを戻すと、ゴミ箱にない一番近い祖先の下に戻る。
  • 削除・戻す・完全に消すは作成者本人だけ。他の人はアーカイブする（D18）。
  • ホームは消せない。ワークスペースは設定で定義するので対象外。

D6. 更新時刻は今のまま（決定: B）

D7. 個人用トークンからの書き込みは人のまま、「API 経由」と添える（決定: B）

個人用トークン（スクリプト用）の書き込みは、いま「人」として残る。自動化した書き込みが人の手書きと区別できない。

  • A. 第 3 の種類「自動化」: ActorKind = automation を足し、画面では「◯◯ のスクリプト」と出す。
  • B. 人のまま、トークン経由であることだけ表示: 書き手の種類は変えず、TokenID があれば「API 経由」と添える。
  • C. 今のまま。
決定: B。種類を増やすと権限や表示の分岐が増える。区別が要るのは表示だけ。

D8. 添付ファイルの概念を足す（決定: A）

D9. 要約は一旦持たない（決定: C）

Paper.Summary は足さない。AI の道案内は、親ペーパーの本文（子を紹介するまとめ）とホームから降りていく形（木）と、検索で行う。必要になったら改めて検討する。

D10. ブロック内のテキストの装飾は記法つき文字列で持つ（決定: A）

ブロックの中の一部だけ色を変える、背景に色を付けるといった装飾が要る。今の本文はインライン Markdown の文字列で、太字・斜体・コード・リンクしか持てず、色は表せない。人の編集欄も記法がそのまま見えるテキスト欄なので、色を付ける操作もない。

これは「テキスト系ブロックの本文とは何か」を決め直すことになる。対象は段落・見出し・引用・リスト・ToDo・コールアウト・表のセル・画像のキャプション。コードと AI だけが書く図は対象外。

表し方

A. 文字列のまま記法を足す
   "手順は[必ず]{.red}守る。**例外なし**"

B. 文字の並び（run）の列として保存する
   [{"text":"手順は"},
    {"text":"必ず","marks":{"color":"red"}},
    {"text":"守る。"},
    {"text":"例外なし","marks":{"bold":true}}]

C. 平文と、範囲で指した装飾
   text:  "手順は必ず守る。例外なし"
   marks: [{"from":3,"to":5,"color":"red"},{"from":8,"to":12,"bold":true}]
観点A. 記法つき文字列B. run の列C. 平文 + 範囲

検証記法を解析しないと正しいか分からない。エスケープの扱いが難しい構造をそのまま検証できる範囲の重なり・はみ出しの検証が要る
検索エントリ・平文化解析して取り出すtext をつなぐだけそのまま
衝突の判定（内容が同じか）文字列の比較列の比較（同じ見た目を必ず同じ形に正規化する）正規化が要る

決定: A（B は保存の形として冗長すぎる）。本文は今と同じ文字列のまま、インライン Markdown に Pandoc の囲み記法 [文字]{.色} を足す。今の本文はそのまま正しい本文なので、移行は要らない。A の弱点は次のように抑える。
  • 文法を閉じる: 使える記法を決めた一覧（太字・斜体・取り消し線・インラインコード・リンク・[文字]{.色}・[文字]{.bg-色}）に限り、それ以外の記法（HTML など）は文字として扱う。エスケープは CommonMark の規則（\[ など）に従う。
  • 保存のときに正規化する: サーバーが本文を解析して、決まった書き方で書き直してから保存する（例: __太字__ は **太字** に、隣り合う同じ色の囲みは 1 つに、空の囲みは消す）。「同じ見た目なら同じ文字列」になるので、衝突の判定（内容が同じか）は文字列の比較のままでよい。
  • 検証: 解析できない本文や、パレットにない色は保存の前に拒否し、どこが悪いかを返す（AI が直せるように）。
  • 検索への影響はない: 検索エントリには記法を取り除いた平文だけを書く（保存と同じトランザクションで、解析して文字だけを取り出す）。[必ず]{.red} は「必ず」、**例**外 は「例外」として索引されるので、記法で語が分断されることも、{.red} のような記法の文字で当たることもない。リンクは表示される文字だけを索引し、URL は入れない。検索結果の抜粋と強調も平文の上で作る。
  • 画面との相互変換: リッチ編集（D11）は本文を解析して編集用の構造にし、保存のときに記法へ戻す。サーバー（Go）と画面（TypeScript）の解析が食い違わないよう、同じ入出力の例（正規化前 → 正規化後 → 平文）を共有のテストにする。

あわせて決めること

  • 装飾の種類: 太字・斜体・取り消し線・インラインコード・リンク・文字色・背景色を候補にする。下線・文字の大きさ・フォントは入れない（見出しや種類で表すもの）。
  • 色の指定: 任意の色（#RRGGBB）ではなく名前つきのパレット（灰・茶・橙・黄・緑・青・紫・桃・赤 など）にする。明暗のテーマでそれぞれ見やすい色に割り当てられ、AI も選びやすい。
  • 正規化の規則: 上のとおり、保存のたびに決まった書き方へ書き直す。規則の一覧はテストの例として持つ。

D11. 人の編集欄は既存のエディタ部品でリッチ編集にする（決定: A）

D10 で色を付けられるようにするなら、人が記法を手で打つ今のテキスト欄では使えない。選んだ文字に色を付ける、見たまま編集する欄が要る。

  • A. 既存のエディタ部品を使う（ProseMirror / Tiptap、Lexical など）: 1 ブロック = 1 つの小さなエディタにし、ブロックの並びは今のまま papers が持つ。日本語入力の扱いが成熟している。
  • B. contenteditable を自作する: 依存は減るが、日本語入力・選択範囲・貼り付けの扱いを全部自分で持つことになる。
決定: A。ブロック内だけをエディタ部品に任せ、ブロックの分割・結合・並びは papers の操作のまま残す。どの部品にするかは、日本語入力の扱いと、D10-A の記法（Markdown + [文字]{.色}）との相互変換のしやすさで選ぶ（実装に入るときに候補を試して決める）。

編集はブロック単位

  • 1 ブロック = 1 つのエディタ。ページ全体を 1 つの文書として編集する形にはしない。エディタ部品の文書構造は 1 ブロックの中身だけを持つ。
  • 書き込みの単位もブロック: ブロックから離れたとき（と、一定時間打鍵が止まったとき）に、そのブロックの update を、編集を始めたときの Rev を元のリビジョンとして送る。これは今の状態を書き換えるだけで、版は作らない。衝突も編集中の印（D3）もブロック単位。
  • ブロックをまたぐ動きは papers の操作にする: 行の途中で Enter は「今のブロックを update + 後ろに新しいブロックを insert」、先頭で Backspace は「前のブロックを update + 今のブロックを delete」、複数段落の貼り付けは「insert の列」。どれも 1 つの操作のまとまりで送る。
  • 複数ブロックの選択: コピーはできる。選んだ範囲に色などを付けるときは、ブロックごとの update をまとめて 1 つの操作のまとまりにする。複数ブロックをまたぐ文字の削除も、ブロックごとの update / delete に分けて送る。

D15. 今の状態と、明示的に保存された版だけを持つ（決定）

commit・リリース・ブロックごとの版という 3 つの概念をまとめ、「版」= 書き手（人か AI）が明示的に保存したペーパーの写しだけにする。自動保存という概念はなく、それ以外は今の状態（編集中の最新版）があるだけ。

  • 書き込みは今の状態をすぐ書き換える。書き込みの記録（commit）は残さない。
  • 版は誰かが保存したときだけできる（v1, v2 …）。システムが勝手に作ることはない。最初の版で正本になる。
  • 履歴の参照と復元はペーパー単位で、版の単位。ブロックごとには行わない。
  • 衝突の判定は、ブロックごとの内部の更新番号 Rev で行う（画面には出さない）。
  • 失うもの: 版と版の間の細かい変化。強行で上書きされた内容や、保存前に消された内容は、版に入っていなければ戻せない。
  • これにより、移動の記録（D22・D32 の MoveID）、commit のまとめ方（D5）、ある時点の組み立て（D37）は要らなくなった。

D16. ペーパーとブロックは 1:N（決定: A）

今は 1:N。ペーパーは本体（タイトル・アクセス・作成者）を持ち、ブロックの平らな並びを持つ。親を持つのは表のセルだけ。もう一つの考え方は、ペーパーの中身を 1 つの「ルートのブロック」にし、ブロック全体を木にするもの（Notion のページがブロックであるのと同じ）。

A. 1:N（平らな並び + 表のセルだけ子）B. ルートのブロック（全体を木にする）
形ペーパー → ブロックの列。入れ子は字下げ（属性）で表すペーパー → ルート → 子 → 孫 …。見出しの下の節、トグル、段組みなどを本当の入れ子で持てる
タイトルペーパー本体に持つ（独立した番号は持たない、D1）ルートの本文がタイトル。衝突・履歴がブロックと同じになる
親の扱い「親なし = ペーパー直下」という特別扱いが 1 つあるどのブロックにも親がある（ルートを除く）。規則が一様
移動と衝突移動は兄弟の間だけ。衝突は 1 ブロック単位で閉じる親をまたぐ移動が増える。「他人が親を消した間に子を直した」のような部分木の衝突を決める必要がある
遅延読み込み並び順キーの範囲で区切って読む（D17）部分木ごとに読める（閉じた節は中を読まない）
ペーパー本体との関係本体（公開範囲・作成者・位置・状態）と中身がはっきり分かれるルートのブロックと本体の 2 つに情報が分かれる。どちらに何を持つかを決める必要がある
決定: A（1:N）を維持。ペーパーは「公開範囲・作成者・木の中の位置・状態」を持つ入れ物で、中身とは性質が違う。木にすると移動と衝突の規則が一段難しくなる一方、今ほしい表現（節、リストの入れ子）は見出しと字下げで足りている。トグルや段組みのような本当の入れ子が要ると決まったら、そのとき B を見直す（その場合も、ペーパー本体はブロックにしない）。

D17. ブロックが大量にあるペーパーの読み込み（決定: 推奨どおりすべて入れる）

全社の情報を集めると、AI が長い資料をそのまま取り込んで数千ブロックのペーパーができる。今は開くたびに全ブロックを読み、しかも 3 回読んでいる（画面の読み込み、変更の購読を始めるときのリスナーの初回、接続後の読み直し）。2,000 ブロック（約 2 MB）なら 1 回開くだけで 6,000 件の読み取りと数 MB の転送になる。

遅延読み込みの形

  • 範囲で読む: ペーパー直下のブロックを並び順キーの順に N 件ずつ読み、続きはカーソル（最後のキー）で読む。範囲内の表は、そのセルも一緒に読む。索引は既存の (ParentID, Order) で足りる。
  • 途中から読む: 検索で当たったブロックへ飛ぶときは、そのブロックの並び順キーの前後を読む。
  • 画面: 見えている範囲だけ描き（仮想スクロール）、近づいたら続きを読む。
  • AI: papers_read_paper は「見出しの目次 + 先頭の N ブロック」を返し、続きは見出しかカーソルを指定して読む。AI は目次を見て必要な節だけ読める。

変更の購読も全件を読まないようにする

今の購読はブロックのコレクション全体にリスナーを張るので、始めるときに全ブロックを読む。そこで、購読の対象をペーパーごとの短命の変更の記録（Event）にする。

  • 購読を始めた時刻以降の記録だけを見る（初回はほぼ空）。記録から変わったブロックの ID を集め、一括取得で読む。
  • 「ブロックの更新時刻が開いた時刻以降」で絞る方法は使えない。開く前からある古いブロックが削除されても、更新時刻では拾えないため。
  • 読んでいない範囲のブロックの変更は、画面が持っていないので捨ててよい（範囲を読むときに最新を読む）。
  • 記録は配信のためだけのもので、一定時間（例: 1 日）で消す。履歴ではない。

要件: ブロックはまとめて読む（N+1 を作らない）11-21 決定

ブロック・ペーパー・版・写しを、ループの中で 1 件ずつ読まない。ID の列が分かっているものは 1 回の一括取得で読み、条件で絞るものは 1 本のクエリにする。リポジトリの口（インターフェース）にも一括取得を用意し、1 件ずつの取得をループで呼ぶ書き方をなくす。

印刷（範囲読みと仮想スクロールの影響）

見えている範囲だけを描くと、ブラウザの印刷は描いた部分しか出さない。印刷では必ずペーパー全体を出す。

  • 印刷の入口を用意する: 画面のメニューに「印刷・PDF」を置き、押したら残りのブロックをすべて読み（一括取得、N+1 なし）、仮想スクロールを止めて全体を描いてから印刷を開く。読み込み中は進み具合を出す。
  • ブラウザの印刷（Ctrl+P）を直接使われたとき: 印刷の直前（beforeprint）には非同期の読み込みを待てない。小さなペーパー（全体を最初から読んでいるもの）はそのまま全体が出る。大きなペーパーで読み込みが済んでいなければ、印刷用の表示の先頭に「一部しか含まれていません。メニューの『印刷・PDF』を使ってください」と出す（黙って欠けたまま印刷しない）。
  • 何を印刷するか: 既定は開いているもの（今の状態）。/latest や /v/{番号} を開いていればその版。用紙の上に、タイトル、パス、状態（v3・正本 / 下書き）、印刷した日時を入れる。
  • 子ペーパー: ペーパーブロックは子のタイトルとして出す（中身は含めない）。「配下も含めて印刷」を選んだときだけ、配下を本文の順に続けて出す（配下を集めるのは裏の処理なので、大きければ時間がかかると伝える）。
  • 見た目: サイドバー・編集中の印・操作ボタンは出さない。ブロックの途中や表の行の途中で改ページしないようにし、長い表は各ページに見出し行を繰り返す。文字色・背景色は印刷でも読めるパレットの値を使う（D10）。
  • AI のみの図（mermaid / svg / html）: iframe のまま印刷すると欠けたり 1 ページに収まらなかったりするので、印刷のときは描いた結果（SVG か画像）を本文に置き換えて出す。
決定: すべて入れる。順番は (1) 開くときの重複読み（3 回 → 1 回）をなくす、(2) 購読を変更の記録にする、(3) 範囲読みと AI の目次、(4) 画面の仮想スクロール。(1)(2) はブロック数に関係なく効く。

D12. 規則がないワークスペースはログイン済み全員が使える（決定: A）

ロールを持たないので、規則は hecatoncheires と同じく allow の 2 値を返す（決定）。残るのは、[authz] を書かなかったワークスペースの既定。

  • A. ログイン済み全員が使える: ログインできる人は全体設定（許可するメールのドメインなど）で絞られている前提。hecatoncheires と同じ。
  • B. 誰も使えない: 規則の書き忘れで全員に見えることがない。
決定: A。社内の知識を集める道具として、既定で開いているほうが使われる。閉じたい内容は private のペーパーか、規則のあるワークスペースに置く。起動時に「規則のないワークスペース」を一覧でログに出す。

D18. 削除は作成者だけ、他の人はアーカイブ（決定）。private の招待は将来

削除とアーカイブ

  • 削除（ゴミ箱へ入れる・ゴミ箱から戻す・完全に消す）ができるのは、そのペーパーの作成者本人だけ（AI が作ったペーパーなら代理元のユーザー。本人の代理の AI も含む）。
  • 他の人はアーカイブする。アーカイブしたペーパーは、検索・一覧・サイドバーの最近開いたもの・AI の道案内から除かれる。URL では開け、木の中の位置もそのまま（親の本文のペーパーブロックは「アーカイブ済み」として薄く出す）。アーカイブを解くのは、そのペーパーを使える人なら誰でも。
  • 配下があるとき: 削除は配下ごとなので、配下がすべて自分の作ったペーパーのときだけ削除できる。他の人のペーパーが含まれていれば、削除の代わりに「配下ごとアーカイブ」を案内する（他の人のペーパーを本人以外が消すことはない）。
  • 親の本文でペーパーブロックを消す操作: 子の作成者本人なら子を配下ごとゴミ箱へ。本人でなければ、ブロックは消さずに子を配下ごとアーカイブする（画面は「削除できるのは作成者だけです。アーカイブしますか」と確かめる）。
  • 作成者がいなくなったペーパー: 誰も削除できない。アーカイブはできる。データはデプロイ側の管理コマンドでだけ消せる。
  • ホームは削除もアーカイブもできない。

private を誰が見られるか

  • 当面は作成者だけ。将来、private のペーパーに人を招待（invite）できるようにする。招待の単位（当面はユーザー）、招待された人ができること（読むだけか書けるか）、招待された人の画面のどこに出すか（private は木の外にあるので「共有された」一覧など）、招待した人がいなくなったときの扱いは、後で考える。

D13. 設定から消えたワークスペースのデータは残して見えなくする（決定: A）

ワークスペースは設定から外せるが、ペーパーは保存先に残る。id を変えた場合も、古い id のデータが取り残される。

  • A. 残して見えなくする: データは消さず、どの主体からも見えない。設定に戻せば元どおり見える。起動時に「設定にないワークスペースのデータがある」と警告する。
  • B. 管理コマンドで消す・移す: A に加えて、papers workspace purge（消す）と papers workspace rename（id を付け替える）を用意する。
決定: A。設定の書き間違い 1 つでデータが消えないことを優先する。データは消さず、どの主体からも見えない。設定に戻せば元どおり見える。起動時に「設定にないワークスペースのデータがある」と警告する。消す・付け替える管理コマンド（B）は、必要になってから検討する。

D14. グループは一旦持たない（決定）

ユーザーのグループという概念を当面なくす。使える人の規則（Rego）は、ユーザーの ID・メール・メールのドメインで書く。

  • 今の保存先のグループ（Group）と、グループ管理の API・画面はなくす。
  • 必要になったら、組織の正本（Google Workspace のグループなど、IdP）から取り込む形で改めて検討する。papers の中でグループを管理する形には戻さない。
