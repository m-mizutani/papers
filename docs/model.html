papers モデルと概念

papers が扱うものを、言葉の意味・持つ値・守る約束・一生の流れまで一つずつ定める。コードを読まなくても、何を保存し、何が起きたら何が変わるかが分かることを目指す。

用語

画面・API・コード・この文書で同じ言葉を同じ意味で使う。英語名はコードと API の名前。

全体の関係

保存の階層もこの入れ子のとおり（workspaces/{ws}/papers/{p}/blocks/{b}/versions/{n}、…/papers/{p}/commits/{c}、workspaces/{ws}/search/{…}）。ユーザー・グループ・トークン・セッションはワークスペースの外にある。

ワークスペース

ペーパーの入れ物で、権限の基本単位。「チーム」や「部署」くらいの粒度を想定する。ワークスペースをまたぐ操作（移動・横断検索）はない。

ID
papers が発行する UUIDv7。変わらない。
Name / Description / Emoji
表示用。名前は必須。
Bindings
割り当ての列。同じ主体は 1 回だけ。所有者の割り当てが常に 1 つ以上ある（なくなる変更は拒否）。
CreatedBy / CreatedAt / UpdatedAt
作成者は作成時に所有者として割り当てられる。
  • 作成できる人は設定で決まる（全員、または管理者だけ）。
  • 削除・アーカイブはまだない（決めること D4 で一緒に扱う）。

ペーパー

タイトルとブロックの並び。人も AI も同じペーパーを同じ操作で書く。ペーパー全体の通し番号（リビジョン）は持たない。履歴はブロックごとの版と、commit の列で表す。

ID / WorkspaceID
不変。ペーパーはワークスペースをまたいで移動しない。
Title
1 行、256 バイトまで。空でもよい（画面では「無題」）。版を持たない（D1）。
Access
制限の有無と、ペーパー独自の割り当て。意味はロールと権限。
CreatedBy
作成した書き手。人が作ったペーパーは、その人が編集者以上である限り所有者になる。
UpdatedAt / UpdatedBy
おおよその最終更新。ペーパー本体への書き込みを減らすため、タイトル変更か、前回から 1 分以上たった commit のときだけ更新する。最大 1 分遅れる（D6）。

なぜペーパー本体をほとんど書かないか

Firestore は 1 つのドキュメントに毎秒 1 回程度しか書けない。全員の commit がペーパー本体を書くと、そこが詰まる。だから履歴はブロック側に持ち、ペーパー本体はタイトル・アクセス・おおよその更新時刻だけにした。

ブロック

編集・版・衝突・検索エントリの最小単位。ブロックは内容（種類・本文・属性）と位置（親・並び順キー）を持ち、この 2 つを分けて扱う。

ID
UUID。クライアントが決めてもよい（画面に先に出すため）。一度使った ID は、削除後も同じブロックのものとして扱う（復元で戻る）。
Type
種類。下の表のどれか。
Content
本文。意味は種類ごとに違う（下の表）。256 KiB まで。
Props
種類ごとの属性。その種類に関係ない属性は保存前に消す（種類を変えても古い属性が残らない）。
ParentID
親ブロック。表のセルだけが親（表）を持つ。それ以外は空（ペーパー直下）。木は 1 段だけ。
Order
兄弟の間の並び順キー（分数インデックス）。2 つのキーの間には必ず別のキーが作れるので、挿入や移動で他のブロックを書き換えない。同じキーになったら ID の順。
Version
1 から始まり、内容か位置が変わるたびに 1 増える。欠番なし。
CreatedBy / UpdatedBy
最初の書き手と、最後に変えた書き手（時刻つき）。

ブロックの一生

版

ブロックの状態の、不変で完全な写し。commit はブロックの本文を持たず、版の番号だけを指すので、どんなに大きなブロックでも commit は小さい。

  • 番号: ブロックごとに 1 から欠番なしで増える。同じ番号を 2 度書くことはできない（保存先で作成のみ許す）。2 人が同時に同じ番号を作ろうとしても、片方は失敗してやり直す。
  • 中身: その時点のブロック全体（内容・位置・書き手・時刻）。
  • 寿命: ペーパーを削除するまで残る。ブロックを削除しても残る。
  • 削除は版にしない: 削除は commit の変更として残り（誰がいつ）、版の列には足さない。最後の版が「削除される直前の状態」になる。
  • 内容の比較: 2 つの版は、種類・本文・属性がすべて同じなら「内容が同じ」。位置と書き手は比べない。

操作と commit

書き手は操作（Op）の列を 1 つの commit として送る。全部適用されるか、何も適用されないかのどちらか。結果は変更（Change）の列として commit に残る。操作は頼みごと、変更は起きたことで、1 つの操作が複数の変更を生むこともある（表を挿入するとセルも挿入される）。

操作必須の値元の版生む変更何も起きないとき
insert種類（位置は after）不要insert（表ならセルの insert も）—
updateブロック必須update（表の形が変わればセルの insert / delete も）内容が変わらない
deleteブロック必須delete（表ならセルの delete も）他の人がすでに削除していた
moveブロック（位置は after）不要move位置が変わらない、または削除済み
restoreブロック、戻す版存在するなら必須restore内容が戻す版と同じ
set_titleタイトルなし（D1）set_titleタイトルが同じ
insert_markdownMarkdown不要insert の列—

commit の約束

  • 変更が 1 つもなければ commit は作らない（何も起きなかった、が答え）。
  • 1 commit で変えられるブロックは 240 まで、書く本文の合計は 3 MiB まで。超えたら分けてもらう。
  • commit の順序は作成時刻（同時刻なら ID 順）。ペーパー全体の通し番号はない。
  • メッセージは任意。AI には短い説明を書くよう求める。人の画面からの保存はメッセージなし。
  • commit 自体は不変。消すのはペーパーを削除したときだけ。

人の画面はブロックから離れるたびに保存するので、commit が細かく大量にできる（D5）。

元の版と衝突

ロックは持たない。書き手が「どの版を見て書いたか」を添え、その後に他の書き手が内容を変えていたら、気づかないまま消さないように一度止める。決めた経緯は同時編集の設計にある。

判定の規則

操作がブロック b を元の版 n で書き換えようとしたとき、b のこの commit が始まる前の状態を cur とする。

状況結果
n がない、または 0不正な要求（400）
n > cur の版不正な要求（読んでいない版を元にしている）
n = cur の版そのまま適用
n < cur の版で、版 n と cur の内容が同じ（移動だけされた、変えて元に戻された）そのまま適用。衝突ではない
n < cur の版で、内容が違う衝突。強行なら上書きして「上書きした版と書き手」を残す
b が他の書き手に削除されていた更新・復元は衝突（強行でも。先に復元が必要）。削除・移動は何もしない
b がこの commit の中で作られた判定しない
  • commit の中に衝突が 1 つでもあれば、何も書かずに全部を返す（409、衝突ごとに cur を添える）。書き手は全体を見て直せる。
  • 「この commit が始まる前の状態」と比べるので、同じ commit の中で同じブロックを 2 回触っても、自分の 1 回目とは衝突しない。
  • 人の画面は編集を始めた時点の版を送る。保存直前に受け取った最新版を送ると、編集中に届いた他人の変更を見逃す。

衝突しないもの（意図して）

  • 位置: 並び替えは後勝ち。並びが入れ替わっても内容は失われない。
  • タイトル: 今は後勝ち（D1）。
  • 表の形の変更で消えるセル: 今は確認なしに消える（D2・D3）。
  • アクセス設定: 所有者だけが変えるもので、同時に変える場面は少ない。後勝ち。

書き手と主体

主体はリクエストの時点で「誰が、どの権限で」を表し、権限の計算に使う。書き手は変更に焼き付けて残す記録で、後で名前が変わっても書き換えない。

主体（Principal）書き手（Actor）
いつリクエストごとに作る。保存しない書き込みのたびに作り、commit・ブロック・版に残す
中身ユーザー、所属グループ、システム管理者か、使ったトークン人か AI か、代理元のユーザー、その時点の表示名、AI の名前、トークン
用途ロールの計算「誰が書いたか」の表示と、上書きされた人の特定

人と AI の区別

入り方書き手の種類表示
Web UI（セッション）人ユーザー名
AI 用トークン（REST / MCP）AI「Claude（Alice の代理）」
MCP をセッションで使う（開発モード）AI「MCP client（… の代理）」
個人用トークン（スクリプト）人ユーザー名（D7）
  • AI は必ず誰かの代理。権限はその人のものを借り、トークンで上限をかける。AI 単独の利用者はいない。
  • ユーザーは papers が発行する ID を持ち、Google などの外部の ID とは Identity で結びつける。1 人が複数の外部 ID でログインできる。

ロールと権限

ロールの決まり方

  1. ワークスペースのロール = ワークスペースの割り当てのうち、主体に当てはまるものの最大。システム管理者は所有者。
  2. ペーパーのロール:
    • ワークスペースの所有者 → 所有者
    • 人がペーパーを作り、いまもワークスペースの編集者以上 → 所有者
    • 制限なしのペーパー → max（ワークスペースのロール, ペーパーの割り当て）
    • 制限ありのペーパー → ペーパーの割り当てだけ
  3. トークンを使っていれば上限をかける: 読み取り用 → 閲覧者、書き込み用 → 編集者、許可したワークスペースの外 → なし。トークンで所有者の操作はできない。

主体に当てはまる割り当て: ユーザー本人、所属するグループ、メールのドメイン、ログイン済み全員。グループは全社共通で、管理者が管理する。

操作ごとに必要なロール

操作必要なロール
ペーパーを読む・履歴を見る・変更を受け取る・検索で見つけるそのペーパーの閲覧者
ペーパーの一覧ワークスペースの閲覧者（または、見えるペーパーが 1 つ以上ある）
ペーパーを作るワークスペースの編集者
ブロックを書く・タイトルを変える（commit）そのペーパーの編集者
アクセス設定を変える・ペーパーを削除するそのペーパーの所有者
ワークスペースの設定と割り当てを変えるワークスペースの所有者
グループを管理するシステム管理者

読めない相手には「存在しない」（404）を返し、ペーパーやワークスペースがあることを漏らさない。読めるが足りない相手にだけ 403 を返す。

派生データ

検索エントリ

  • タイトル 1 つと、平文を持つブロック 1 つごとに 1 件。ワークスペースごとに置く（検索の範囲をパスで切るため）。
  • ブロックと同じトランザクションで書く。commit が見えた時点で検索にも当たる。
  • 正本ではない。すべてペーパーとブロックから作り直せる。
  • 権限の情報は持たない。検索の後で、ペーパーのロールで絞る。

変更フィード

  • ブロックの更新・削除、ペーパーの更新・削除を、変更後の状態として届ける。何度届いても、順番が入れ替わっても、版を比べて反映すれば同じ結果になる。
  • 取りこぼしは許す設計。接続し直したら必ず読み直す。受け手が遅れたら切って読み直させる。
  • commit そのものは流さない（履歴は必要なときに読む）。

不変条件

どの書き方をしても、保存されたデータが常に満たすこと。保存先の契約テストと use case のテストで守る。

  1. ワークスペースには所有者の割り当てが 1 つ以上ある。
  2. 割り当ての主体は、1 つの割り当ての列の中で重複しない。
  3. ブロックはちょうど 1 つのペーパーに属し、ペーパーはちょうど 1 つのワークスペースに属する。どちらも移動しない。
  4. 親を持つのは表のセルだけで、その親は同じペーパーの表。表のセルは (行, 列) が重ならず、表の行数・列数の範囲にちょうど揃う。
  5. ブロックの属性には、その種類に関係する値しか入っていない。区切り線と表の本文は空。
  6. ブロックの版は 1 から欠番なしで、各番号の写しはちょうど 1 つあり、二度と変わらない。現在のブロックは最大の番号の写しと一致する。
  7. 削除されたブロックの版の列は残る。復元されたブロックの版は、削除前の最後の番号の次から続く。
  8. commit は全部の変更が保存されるか、1 つも保存されないかのどちらか。commit・ブロック・版・検索エントリは同じトランザクションで書かれる。
  9. commit の変更が指す版（変更前・変更後）は、そのブロックの版の列に存在する。
  10. 強行しない限り、元の版の後に他の書き手が変えた内容が、知らないうちに消えることはない。
  11. 強行で上書きした変更には、上書きされた版の番号と書き手が残る。
  12. すべての変更には書き手があり、AI の書き手には必ず代理元のユーザーがある。
  13. 検索エントリは、タイトルと平文を持つブロックにちょうど 1 件ずつあり、内容が一致する。
  14. ペーパーの更新時刻は、最後の commit の時刻より最大 1 分（設定値）までしか遅れない。

決めること

モデルを詰める中で見つかった、曖昧さや穴。どれも推奨を付けたが、決まるまで実装は変えない。

D1. タイトルにも版を付けるか

タイトルだけが版を持たず、同時に変えると後勝ちで黙って消える。履歴には変更前後が残るが、復元の操作はない。

案内容良い点気になる点
A. ペーパーに版を足すPaper.TitleVersion を持ち、set_title に元の版を必須にする。規則はブロックと同じ小さい変更で済む。タイトル変更時はもともとペーパー本体を書いているタイトルの過去の値は commit から拾う（版の写しはない）
B. タイトルをブロックにする種類 title のブロックを先頭に 1 つ置き、ペーパー本体には写しを持つ版・衝突・復元・検索がブロックと完全に同じ正本と写しの 2 か所になる。一覧の表示のために写しの同期が要る
C. 今のまま後勝ち何もしない同時に名前を付け直すと片方が消える
推奨: A。タイトルを同時に変える場面は少なく、規則をブロックと揃えられれば十分。B は概念は美しいが、写しの同期という新しい不変条件を増やす。

D2. 表のセルの指し方

いまセルは「行番号・列番号」で場所を持つ。そのため、途中に行を挿入できない（後ろのセル全部の番号を書き換えることになり、全部の版が上がって衝突も起きる）。また、行や列を縮めると、そこにあるセルが確認なしに消える。

案内容良い点気になる点
A. 今のまま（番号）行・列の追加・削除は末尾だけ単純途中への挿入・並び替えができない。縮めると確認なしに消える
B. 行・列の ID表の属性に行・列の (ID, 並び順キー) の列。セルは (行 ID, 列 ID)。行・列の挿入・削除・並び替えを専用の操作にする途中への挿入や並び替えで既存のセルが変わらない。削除するセルが明確になる表の属性が大きくなる（行 100 × 列 20 なら 120 個の ID）。操作が増える
推奨: B。表は AI がよく書き、人が直す代表的な場面。行の挿入ができない表は使いにくく、番号のずれは衝突と大量の版を生む。表全体の復元（削除済みの表を戻す）も、行・列の ID があれば「表の版 + 各セルの最後の版」で組み立てられる。

D3. 行・列を消すとき、他の人が直したばかりのセルをどうするか

セルは 1 ブロックとして衝突を判定するが、表を縮める・行を消す操作はセルの元の版を持たないので、他の人の直したばかりのセルが確認なしに消える（版は残る）。

  • A. 消すセルの元の版を添えさせる: 行の削除にその行のセルの版を付け、変わっていれば衝突。D2-B と組み合わせると自然。
  • B. 中身のあるセルを消すときだけ確認する: 画面で確認し、API は何も見ない。
  • C. 今のまま: 消えても版から戻せる、とする。
推奨: A（D2-B と一緒に）。他のブロックと同じ「知らないうちに消さない」を表にも通す。

D4. ペーパーとワークスペースの削除を戻せるようにするか

いまペーパーの削除はすぐに全部消え、戻せない。知識を集める場所として、消えて困るのは削除のほうが大きい。

  • A. ゴミ箱: Paper.DeletedAt を付けて隠すだけにし、30 日後に本当に消す。所有者は戻せる。一覧・検索・読み取りは削除済みを除く。ワークスペースも同じ（アーカイブ）。
  • B. 今のまま: すぐ消す。
推奨: A。検索エントリは削除時に消し、戻すときに作り直す（派生データなので）。

D5. commit の粒度と履歴のまとまり

人の画面はブロックから離れるたびに保存するので、1 人が数分書くだけで commit が何十もできる。履歴が読みにくく、保存量も増える。

  • A. 保存はそのまま、見せ方でまとめる: 同じ書き手が続けて 5 分以内に行った commit を、履歴の画面で 1 つの「編集のまとまり」として折りたたむ。保存のモデルは変えない。
  • B. 保存をまとめる: 画面が一定時間ためてから送る。衝突の窓が広がる。
  • C. 今のまま。
推奨: A。衝突の窓は短いほうがよく、まとまりは見せ方の問題として扱える。「まとまり」は保存しない派生の概念にする。

D6. ペーパーの更新時刻の意味

UpdatedAt は最大 1 分遅れるが、名前からは正確な時刻に見える。一覧の並びや「◯分前に更新」の表示に使っている。

  • A. 名前と説明で正直にする: TouchedAt（おおよその最終更新）に改名し、API でもそう説明する。正確な時刻が要るときは最新の commit を読む。
  • B. 今のまま（名前は UpdatedAt、説明だけ足す）。
推奨: A。名前が意味と合っていないと、後で正確さを前提にした機能が作られる。

D7. 個人用トークンからの書き込みを誰として残すか

個人用トークン（スクリプト用）の書き込みは、いま「人」として残る。自動化した書き込みが人の手書きと区別できない。

  • A. 第 3 の種類「自動化」: ActorKind = automation を足し、画面では「◯◯ のスクリプト」と出す。
  • B. 人のまま、トークン経由であることだけ表示: 書き手の種類は変えず、TokenID があれば「API 経由」と添える。
  • C. 今のまま。
推奨: B。種類を増やすと権限や表示の分岐が増える。区別が要るのは表示だけ。

D8. 画像の置き場所

画像は外部 URL だけで、ファイルを置けない。社内の情報を集めるなら、外部 URL は消えたり見えなくなったりする。

  • A. 添付ファイルの概念を足す: ペーパーに属する Attachment（Cloud Storage に保存、権限はペーパーに従う）。画像ブロックは添付を指せる。
  • B. 今のまま（外部 URL のみ）。
推奨: 当面 B、早めに A を設計。モデルとしては「ペーパーに属し、版を持たない不変のファイル」で足りる。

D9. AI が道案内に使う「要約」をペーパーに持つか

全社の情報を集めると、AI は検索だけで目的のペーパーにたどり着きにくい。人が目次を見るように、AI にもペーパーの要約があると探しやすい。

  • A. Paper.Summary を足す: AI が書き、人も直せる短い要約。一覧・検索・MCP の結果に出す。版は持たず後勝ち。
  • B. 先頭のブロックを要約として扱う慣習にする: モデルは変えない。
  • C. 持たない。
推奨: A を検討（急がない）。AI が主な書き手である papers ならではの概念で、検索エントリとも相性がよい。
