決定事項

papers は、人と AI が同じ「ペーパー」に知識を書き溜める共有キャンバス。主な書き手は MCP / API 経由の AI で、人間は読んで直す側に回る。現時点で決まっていることは次のとおり。

  • 保存先は Firestore11-21ゼロスケールで安く、リスナーでインスタンス間の配信まで完結する。書き込みのホットスポットは、履歴をブロック単位にして避ける。
  • 履歴の単位はブロック11-21各ブロックがバージョンとスナップショットを持つ。commit は「どのブロックをどの版からどの版にしたか」だけを記録し、ペーパー全体の通し番号は持たない。
  • 同時編集はブロック単位の弱いロックと後勝ち11-20編集中のブロックは他の人と AI に見え、書き込みは拒否される（force で上書き可）。古い版を元にした上書きは記録して通知する。
  • Cloud Run + LB で WebSocket を使う11-20接続は最大 60 分で切れる前提で、クライアントは自動再接続して読み直す。
  • Google SSO と papers 発行のユーザー ID、ロールベースの認可11-20Rego は組織固有のルールが必要になってから追加する。
  • リッチな表現は AI だけが書く11-20Mermaid・SVG・HTML のブロックは AI が書き、UI は描画だけする。HTML は sandbox 付きの iframe で隔離する。

全体像: 書き込みと配信の経路

書き込みはどのインスタンスに届いても Firestore への 1 トランザクションになる。配信はアプリ側の pub/sub を使わず、ペーパーを開いている各インスタンスが Firestore のリスナーで変更を受け取り、自分の WebSocket 接続に流す。

データモデル: ブロックの履歴がペーパーをつくる

ペーパーはブロックの並びで、並び順は fractional index（文字列キー）で決める。挿入や移動で他のブロックを書き換えない。表は table ブロックの子として table_cell を持ち、セル単位で編集・ロックできる。

同時編集

仕組み動き
弱いロックブロックをクリックすると WebSocket 経由でロックを取る。他の人には「◯◯が編集中」と表示され、AI はそのブロックへの書き込みを拒否される。
上書き「それでも編集する」（API では force）でロックを越えて書ける。同じブロックへの同時書き込みは後勝ち。
上書きの記録古い base_version を元に書いた場合は commit に上書きした版を残し、UI で通知する。
配信イベントは変更後の状態（ブロック全体）を運ぶ。クライアントは版を比べて反映するので、重複や順序の入れ替わりがあっても収束する。
再同期接続直後（hello 受信時）に必ず読み直す。受け手が遅れてバッファが溢れたら closing: resync を送り、再接続させる。

認証・認可

認証

  • Google OIDC（authorization code + nonce、ID トークンは JWKS で署名検証）。初回ログインで papers がユーザー ID を発行し、IdP の subject と紐付ける。別の IdP は後から足せる。
  • ログインできる人は許可ドメインと許可メールで決める（Google 利用時はどちらか必須）。システム管理者はメールで指定する。
  • ブラウザはセッション Cookie（秘密値はハッシュで保存）。変更系のリクエストには X-Requested-With: papers ヘッダを必須にして CSRF を防ぐ。
  • API と MCP は Bearer トークン（pap_<id>.<secret>）。MCP はブラウザ Cookie を受け付けない。トークンはブラウザのセッションからだけ発行できる。

認可

規則内容
ロールviewer < editor < owner。付与先はユーザー、グループ、メールドメイン、サインイン済みの全員。
ワークスペースバインディングの最大値。システム管理者は全体の owner。
ペーパーワークスペースの owner は全ペーパーの owner。作成者は editor 以上である限り owner。限定公開ペーパーはペーパー側のバインディングだけで判定し、公開ペーパーではペーパー側のバインディングでロールを上げることだけができる。
トークンread は viewer、write は editor が上限。トークンは共有設定の変更やグループ管理などの権限管理ができない。
見え方読めないものは 404、読めるが権限が足りないものは 403。存在を漏らさない。

API と MCP

  • REST /api/v1/...: ワークスペース、ペーパー、POST .../commits（複数 op をアトミックに適用）、commit 履歴（新しい順、カーソル）、ブロックの版履歴、ロック、Markdown 書き出し、検索、トークン、グループ。
  • WebSocket GET .../papers/{id}/live: lock / unlock / heartbeat を送り、block_put / block_deleted / paper_updated / lock / unlock を受け取る。
  • MCP（Streamable HTTP、stateless）: papers_guide、papers_list_workspaces、papers_list_papers、papers_search、papers_read_paper、papers_create_paper、papers_commit、papers_history、papers_block_history。
  • insert_markdown op を使うと、AI は Markdown 1 本でまとめて書ける。mermaid / svg / html のコードフェンスはリッチブロックに、GFM の表は表ブロックになる。

commit のトランザクション

Firestore のトランザクションは読み込みをすべて先に済ませる必要がある。そのため実装では書き込みをメモリに積み、読み込みにはそれを重ねて見せ、最後にまとめて書く。

read   papers/{p}                    共有ロック。書くのはタイトル変更か更新時刻が古いときだけ
read   blocks/{id}                   変更するブロック
query  blocks where ParentID == X and Order > Y order by Order limit k   挿入位置
------ ここから書き込み
set    blocks/{id}
create blocks/{id}/versions/{v}      Create なので同じ版の二重書き込みは失敗する
delete blocks/{id}
create commits/{c}
set    papers/{p}                    必要なときだけ
  • 1 トランザクションの書き込み上限 500 に収めるため、1 commit で変更できるのは 240 ブロックまで（1 変更でブロックと版の 2 書き込み）。表は 200 セルまで。
  • 同じ位置への同時挿入は同じ順序キーになりうる。並びは（順序キー、ID）で決まり、次の挿入は「順序キーが厳密に大きい次の兄弟」との間にキーを作るので壊れない。

インデックスと TTL

複合インデックスは blocks の (ParentID ASC, Order ASC) と (ParentID ASC, Order DESC) の 2 本だけ。本文（最大 256 KiB）は単一フィールドインデックスから外す。定義は deploy/firestore.indexes.json。

gcloud firestore indexes composite create --collection-group=blocks \
  --field-config=field-path=ParentID,order=ascending --field-config=field-path=Order,order=ascending
gcloud firestore indexes composite create --collection-group=blocks \
  --field-config=field-path=ParentID,order=ascending --field-config=field-path=Order,order=descending
gcloud firestore indexes fields update Content --collection-group=blocks --disable-indexes
gcloud firestore indexes fields update Content --collection-group=versions --disable-indexes
gcloud firestore fields ttls update ExpiresAt --collection-group=sessions --enable-ttl
gcloud firestore fields ttls update ExpiresAt --collection-group=locks --enable-ttl

TTL による削除は最大 24 時間ほど遅れることがあるので、アプリは常に ExpiresAt を見て有効かどうかを判定する。

テスト

契約テスト（pkg/repository/*_test.go）はメモリ実装と Firestore 実装の両方で走る。Firestore は TEST_FIRESTORE_PROJECT_ID があるときだけ実行する。

task test:firestore   # Docker でエミュレータを立てて契約テストを実行

デプロイ

  • Cloud Run + 外部 HTTPS LB。--timeout=3600 で WebSocket を最大 60 分保つ。--min-instances=1 を推奨。
  • WebSocket 接続中はインスタンスに課金されるので、--concurrency は大きめにする。
  • session affinity はベストエフォート。状態はすべて Firestore にあるので、どのインスタンスにつながってもよい。
  • --base-url を https にすると Cookie に Secure が付く（Cloud Run では TLS は LB で終端される）。

未決事項と次のタスク

  1. 全文検索をどう補うか。 今の検索はブロックの全件読みで、ペーパー数に比例して読み取りが増える。Vertex AI Search、ベクトル検索、別ストアのどれにするか。
  2. リスナーの課金。 接続ごとに 3 リスナーを張るので、同じペーパーを 10 人が開くと読み取りも 10 倍になる。規模が出たらインスタンス内で共有する方式を検討する。
  3. Firestore 実装をエミュレータで検証する。 コンパイルのみ確認済み。本番プロジェクトにインデックスと TTL を設定する。
  4. ワークスペース一覧は全件読み。 ワークスペースが数百を超えたら、メンバーシップの逆引きドキュメントを持つ。
  5. ペーパー削除の後始末。 本体を先に消してから子コレクションを掃除する。途中で失敗した残骸を消すジョブが必要。
  6. 版履歴からの差分表示と巻き戻し。
  7. ペーパー上で AI に依頼する UX。 「ここを書いて」と頼める仕組み。
  8. 組織ポリシーの Rego フック、Terraform。
