決定事項

  • ワークスペースは設定ファイルで定義する--config のディレクトリに 1 ファイル 1 ワークスペースの TOML。[authz] の Rego（data.papers.authz.allow）で使える人を決める。規則がなければログイン済みの全員（起動時に警告）。判定は 60 秒キャッシュし、判定できなければ拒否。画面と API にワークスペースを作る・変える入口はない。
  • ロールはない。ペーパーは public / privatepublic はワークスペースを使える人全員、private は作成者だけ（AI はその代理元）。削除・戻す・完全削除は作成者本人だけで、配下もすべて本人のものに限る。他の人はアーカイブ。システム管理者もいない。
  • すべての ID はサーバーが発行する UUID v4 の base62（22 文字）受け取る ID は形式と v4 であることを検査し、違えば 404。新しいブロックを同じまとまりで指すときは ref と after: "ref:n1"。応答は ref と ID の対応を返す。
  • 今の状態と、明示的に保存した版だけcommit・変更履歴・ブロックの版は廃止。ブロックは内部の Rev（内容が変わると +1）だけを持つ。版はペーパー全体の (ブロック ID, Rev, 親, 位置) の列と、変わったブロックだけの BlockSnapshot。保存は人も AI もできるが、システムは自動で保存しない。
  • 衝突は元の Rev で判定し、一度止めるr なし・r > cur は 400、r = cur は適用、r < cur は衝突（強行で上書き）、他人が削除したブロックの更新は衝突（強行でも）、まとまりの中で作ったブロックは判定しない。1 つでも衝突があれば何も書かず 409 で全部返す。
  • 子ペーパーは親の本文の paper ブロックペーパーは親（ParentID）だけを持つ。移動は 3 件の書き込み。ワークスペースをまたぐ移動は写して元をゴミ箱へ入れ、転送を残す。
  • 配下に及ぶ処理とワークスペースをまたぐ移動は裏の処理（2026-11-22）配下ごとのゴミ箱・戻す・アーカイブと、ワークスペースをまたぐ移動は Job として 200 件ずつのトランザクションに分けて進める。リクエストは裏の処理を作ってすぐに応答し、同じインスタンスが続ける（状態を読む API はない）。期限（60 秒）の切れた裏の処理は他のインスタンスが引き継ぐ。配下の上限（500）は廃止。移動の元は Paper.JobID で書けなくし、写しは終わるまで隠す。
  • 本文は Markdown + 色の囲み[文字]{.red} / {.bg-yellow}。保存前に正規化・検証し、検索には平文を入れる。サーバー（Go）と画面（TS）に同じ実装があり、testdata/markup/cases.json を両方が通す。画面はブロックごとに Tiptap で編集する。

全体像

操作のまとまり（batch）

POST …/papers/{id}/ops（MCP は papers_write）に操作の列と force を送る。pkg/usecase/ops.go の applier が 1 回の RunTx（ワークスペース単位のトランザクション）で適用する。

操作やること元の Rev
insertID を発行して追加。table なら行・列 ID とセル、paper なら子のペーパーも作る。本文は記法を正規化する。不要
update内容（種類・本文・属性）を変える。行・列とセルの位置は変えない。変わらなければ何もしない。Rev は「まとまり前の Rev + 1」。必須
delete削除。表はセルも消す。paper ブロックは消さずに drop の裏の処理を作る（子と配下がすべて本人のものならブロックを消して配下ごとゴミ箱へ、そうでなければ子を配下ごとアーカイブしてブロックを残す）。ブロックが消えるのは配信で届く。必須
move位置だけ変える（Rev は変わらない、衝突しない）。不要
set_title後勝ち（D1）。なし
insert_markdownMarkdown をブロックの列にして insert する。不要
insert_row ほか 6 種表の行・列の挿入（新しいセルも）、削除（そのセルも。編集中の人を editing で返す、D3）、並び替え。見ない
move_paper 他move_paper・set_visibility・save_version・restore_version・archive・unarchive はペーパー単位の操作で、まとまりの中で単独のときだけ受け付ける（専用の REST もある）。不要
  • 上限: 変えるブロック 240、本文 3 MiB、1 ペーパー 5,000 ブロック（insert があるときだけ数える）。操作数は --max-ops-per-batch。
  • 書くもの: ブロック、検索エントリ（ブロックごと、タイトルは _title）、Event（ブロックごと、ペーパーが変わればペーパー）。ペーパー本体はタイトルが変わったときか、UpdatedAt が 1 分以上古いときだけ書く（D6）。
  • 読み取り: トランザクションでは書く前に読む必要があるので、書き込みは最後にまとめて行い、読み取りはまとめた書き込みを重ねて返す（fsTx）。
  • 画面: 新しいブロックは仮のキー（tmp:n）で先に表示して編集を始め、応答の ref 対応で本当の ID に替える。React の key は仮のキーのまま保つので、編集中のカーソルは失われない。

版

  • 保存（SaveVersion）: 今のブロックの (ID, Rev, 親, 位置) とタイトルが最新の版と同じなら何もしない。違えば、最新の版にない (ID, Rev) だけ snapshots/{blockID}_{rev} を書き、versions/{番号} を Create（同じ番号を同時に取ったら片方が失敗）、Paper.VersionNumber を進める。v1 で下書きから正本になる。
  • 読み取り: 版 1 件と、それが指す写しを一括取得して組み立てる。/latest は VersionNumber の版。
  • 差分: 2 つの側（版か今）を (ID, Rev) で突き合わせ、違うものだけ中身を読む。
  • 復元: 今にあって版にないブロックは消し（paper ブロックは削除と同じ規則）、版にあって今にないブロックは同じ ID で戻す。戻すブロックの Rev は max(写しの Rev + 1, 現在時刻のマイクロ秒) に跳ばし、(ID, Rev) が 1 つの中身だけを指し続けるようにする。よそへ移った子・他人のゴミ箱にある子は戻さず not_restored で返す。ゴミ箱から戻る子は、子そのものをまとまりの中で戻し、一緒にゴミ箱に入った配下を restore の裏の処理で戻す。上限はかけない。
  • 画面: 「版を保存」（メモつき）、版の一覧・表示（/v/{n}, /latest）・今との差分・「この版に戻す」。戻す前に /status で保存していない変更を確かめ、先に保存するかを聞く。

木（ペーパーの入れ子）

  • ホーム: 起動時（UseCases.Init）に設定の各ワークスペースについて EnsureHome。workspaces/{ws} の HomePaperID がなければ、記録とホームのペーパーを 1 つのトランザクションで作る。設定から消えたワークスペースの記録があれば警告だけ出す。
  • 子を作る: 親に insert paper（POST …/papers もこれを使う）。private のペーパーは子を持たない。
  • 移動: 元の親の paper ブロック削除、新しい親への追加、本人の ParentID の 3 件。新しい親から 100 段まで親を辿って循環を拒む。親はパスでも指定でき（ResolvePaper、同名が複数なら ambiguous と候補）。
  • ワークスペースをまたぐ移動: move の裏の処理（下）。新しい ID で写し（今の状態と最新の版を v1 に、添付もコピー）、写しをつないでから元をゴミ箱へ入れ、各ペーパーに転送（forwards/{id}）を残す。古い ID を開くと moved（REST はエラーコード、画面は転送先へ移る）。
  • ゴミ箱: DeletedAt と DeletedWith（削除を始めたペーパー）。戻すと同じ DeletedWith の配下も戻り、親がゴミ箱なら近い祖先（なければホーム）に置く。30 日（--trash-retention）を過ぎたものは毎時の処理が添付ごと完全に消す。
  • 配下の扱い: 配下に及ぶ処理（ゴミ箱へ・戻す・配下ごとのアーカイブ）はすべて裏の処理。配下は親インデックス（ParentID in [...]、30 件ずつ）で 1 段ずつ集める。数の上限はない。
  • 子の並び: 親の本文の paper ブロックの順（ListPaperBlocks）で、子のペーパーは一括で読む。
  • サイドバー: ホーム、ピン（開いた段の子だけ読む）、最近開いたもの 10 件、自分の private。GetPaper のたびに最近を更新する。

裏の処理（Job）

pkg/usecase/job.go が進め方（取り出し・期限・再試行）を、job_*.go が種類ごとの段を持つ。対象の数に比例する書き込みは、この形でしか行わない。

  • 保存: workspaces/{ws}/jobs/{job} と、対象のペーパーごとの …/jobs/{job}/items/{paper}（深さ・子を集めたか・済んだか・写しの ID・写した位置）。終われば ExpireAt を 7 日後にして TTL で消す。
  • 期限: 進めるインスタンスは LeaseUntil（60 秒）と自分の ID（起動ごとの乱数）を書き、段ごとに延ばす。段の初めに期限と持ち主を読み直し、他のインスタンスに取られていたら止まる。serve は 15 秒ごとに、設定の各ワークスペースで State が終わっておらず期限の切れた裏の処理を探して取る。
  • 段: 1 段は 1 つのトランザクションで、items を 200 件まで（写しはブロックを 200 件まで）。集める段は未展開の items を読み、子を ParentID in で一括で探して items に足す。当てる段は未処理の items を深さの順に読み、ペーパーに印を付け、items を済みにする。
  • 再試行: ErrInvalidArgument・ErrPermissionDenied・ErrNotFound は規則による失敗で、すぐ failed（戻せる段なら戻す）。他は 2 秒から倍々で最大 5 分まで間隔を空け、20 回で failed。
  • 始め方: リクエストはその場で確かめられることだけを確かめ、裏の処理を保存して応答する。作ったインスタンスが async.Dispatch で進める。ゴミ箱は、集める段で他の人のペーパーが見つかれば配下ごとのアーカイブに切り替わる（D18）。規則による失敗（移動先が消えた、など）はログにだけ残す。
  • 移動の写し: 写しの ID（ペーパー・ブロック・添付）は model.DeriveID(job, 元の ID) で決める（SHA-256 から作る v4 の形）。同じ段をやり直しても同じ文書を書くので、ワークスペースをまたぐトランザクションは要らない。版の v1 はペーパーの最後の段で、まだなければ作る。添付は同じキーに書き直す。
  • 移動の印: 集める段で元の各ペーパーに JobID を付ける。JobID のあるペーパーへの書き込み（ブロック・タイトル・版・移動・公開範囲・削除、子の追加、そこへの移動）は ErrBusy（409 busy）。写しも JobID 付きで作る。JobID のあるペーパーは検索の後で除く（移動の間だけ、元も出ない）。つなぐ段で写しの印を外して根を親の本文に置き、片付ける段で元をゴミ箱に入れて転送を書き、印を外す。つなぐ前に failed なら、写しを PurgePaper で消し、元の印を外す。
  • 見え方: 裏の処理の状態を読む API はない。画面は変更の配信で読み直す。移動が終わった元のペーパーは転送の記録を持ち、開くと（ゴミ箱にあっても）moved で移動先へ案内する。

配信と presence

変更フィードは papers/{id}/events（ExpireAt の TTL で 24 時間後に消える短命の記録）。ブロックの put / delete、ペーパーの更新、版の保存、presence を同じ形で配る。Watch は events のクエリと、完全削除を知るためのペーパー本体の 2 本のリスナーを張り、初回のスナップショットを受け取ってから返す。

  • WebSocket はサーバーから送るだけ（hello / event / closing）。hello のたびに画面は読み直す。追いつけない読者のチャネルは閉じ、再接続・再読み込みさせる。ペーパーが更新されたら見られるかを確かめ直し、見られなくなれば access revoked。
  • presence は POST …/presence（編集の開始と 30 秒ごと、終わりに leaving）で Event に書き、45 秒で切れる。画面は編集中のブロックに名前を出す。行・列の削除は直近の presence を見て、消すセルを編集している人を返す。

認証・認可

認証

Google OIDC（許可するドメイン・メールで入口を絞る）とセッション Cookie、API トークン（pap_{ID}.{秘密}、保存は秘密のハッシュ）。開発用に --no-authn。

認可

  1. ワークスペース: 設定にあり、トークンの許可範囲内で、Rego が allow。入力は {workspace: {id}, user: {id, email, domain}}。
  2. ペーパー: public か、private・ゴミ箱なら作成者本人（Principal.SeesPaper）。
  3. 書き込み: 読み取り用トークンは 403。他はすべて、見えなければ 404。
  4. 作成者だけ: 公開範囲の変更、削除・戻す（配下も本人のもの）。ホームは削除・アーカイブ・移動・private 化できない。

書き手（Actor）は人・AI（トークンの種類 agent）・system（ホームの作成）。個人用トークンの書き込みは人のまま、token_id で「API 経由」と出す（D7）。

Enterprise はインデックスを自動で作らず、インデックスのないクエリは全件走査になる。使うクエリはすべて firestore.RequiredIndexes に並べ、papers firestore setup が足りないインデックスと TTL を作る。主なもの: papers の ParentID（子）、Visibility + CreatedBy.UserID（private）、CreatedBy.UserID + DeletedAt・DeletedAt（ゴミ箱）、blocks の ParentID + Order（範囲読み・挿入位置）と Type + Order（子の並び）、versions の Number、events の Event.At、attachments の SHA256、jobs の State + LeaseUntil（期限切れ）、items の Expanded + Depth・Done + Depth（未展開・未処理）、search の全文インデックス。

契約テスト（pkg/repository/*_test.go）はメモリと Firestore の両方に同じ期待をかける。Firestore 側はエミュレーターか実データベース（TEST_FIRESTORE_PROJECT_ID）で走る。読み取り回数は usecase のテストで数え、子ペーパーの一覧が 1 回の一括取得で済むことを確かめる。

検索

検索エントリはブロックごと（記法を除いた平文）とタイトルごとに、同じトランザクションで書く。Firestore Enterprise の Search ステージ（ワークスペースのコレクション単位）で探し、当たりのペーパーを一括で読んで、見えないもの・ゴミ箱・アーカイブ（指定がなければ）を除く。除いた分を見込んで上限の 4 倍を求める。「この配下で」は当たりのペーパーの親を 1 段ずつ一括で読んで絞る。

添付

画像だけ（PNG・JPEG・GIF・WebP、20 MiB まで）。1 つのペーパーに属し、変わらない。保存先は --attachment-backend（gcs: Cloud Storage の JSON API、dir: ローカルのディレクトリ、memory）。キーは workspaces/{ws}/papers/{p}/attachments/{id}。同じペーパーに同じ中身を貼れば同じ添付を返す。image ブロックは同じペーパーの添付しか指せない。配信はサーバーを通し、読む人の権限を確かめる（署名 URL は使わない）。

デプロイ

  • Cloud Run + 外部 HTTPS LB。--timeout=3600 で WebSocket を最大 60 分保つ。最小 2 インスタンス。
  • 設定ファイル（--config のディレクトリ、--global-config）はイメージかマウントで一緒に届ける。起動時にすべて検証し、1 つでも不正なら起動しない。変更は再起動で反映する。
  • papers firestore setup でインデックスと TTL（sessions, events, jobs, items）を作る。
  • 裏の処理は応答の後も同じインスタンスで続けるので、CPU を常に割り当てる（--no-cpu-throttling）。割り当てない場合も、最小インスタンスの 15 秒ごとの見回りが期限切れを拾うので止まりはしないが、遅くなる。
  • --base-url が https なら Cookie に Secure を付ける。

規模

前の見積もり（同時接続 300、開かれているペーパー 30、編集中 60 人）の結論は変わらない。書き込みはブロック・検索エントリ・Event で 1 編集あたり 3 件程度、毎秒十数件で、ドキュメント単位の毎秒 1 回の目安を大きく下回る。ペーパー本体は 1 分に 1 回までしか書かない。

注意点は 2 つ。1 本の gRPC 接続あたりストリームは 100 本までで、Watch は接続ごとに 2 本張るので、1 インスタンスに 50 接続を超えるなら、インスタンス内でペーパーごとにリスナーを共有するか接続プールを増やす（未決事項）。もう 1 つは版の保存で、1 版あたり変わったブロックの写しと版の文書 1 件を書く。版の文書は全ブロックの (ID, Rev, 親, 位置) を持つので、5,000 ブロックで約 400 KB と 1 MiB の上限に収まる。

未決事項と次のタスク

  • Firestore 実装を実データベースで検証する。 契約テストはメモリ実装で通しているが、この環境にはエミュレーターがなく Firestore 側は未実行。task test:firestore と Query Explain でインデックスの利用を確かめる。
