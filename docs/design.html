決定事項

papers は、人と AI が同じ「ペーパー」に知識を書き溜める共有キャンバス。主な書き手は MCP / API 経由の AI で、人間は読んで直す側に回る。現時点で決まっていることは次のとおり。

  • 保存先は Firestore Enterprise エディション（Native モード）11-21ゼロスケールで安く、リスナーでインスタンス間の配信まで完結し、全文検索も DB の中で済む。書き込みのホットスポットは、履歴をブロック単位にして避ける。リポジトリ層はインターフェースの裏に隠し、別の DB に移せる形を保つ。
  • 検索は Firestore の全文検索11-21ワークスペースごとの検索エントリをブロックと同じトランザクションで書き、Search ステージで引く。use case 層でペーパーやブロックを総なめにする検索はしない（検索）。
  • 履歴の単位はブロック11-21各ブロックがバージョンとスナップショットを持つ。commit は「どのブロックをどの版からどの版にしたか」だけを記録し、ペーパー全体の通し番号は持たない。
  • 同時編集はブロック単位の弱いロックと後勝ち11-20編集中のブロックは他の人と AI に見え、書き込みは拒否される（force で上書き可）。古い版を元にした上書きは記録して通知する。
  • Cloud Run + LB で WebSocket を使う11-20接続は最大 60 分で切れる前提で、クライアントは自動再接続して読み直す。
  • Google SSO と papers 発行のユーザー ID、ロールベースの認可11-20Rego は組織固有のルールが必要になってから追加する。
  • 利用規模は瞬間最大 300 人11-21この規模で、今の「接続ごとに Firestore リスナーを張る」方式は gRPC のストリーム上限に当たる。インスタンス内でリスナーを共有する方式に変える案を検討中（規模の見積もり）。
  • リッチな表現は AI だけが書く11-20Mermaid・SVG・HTML のブロックは AI が書き、UI は描画だけする。HTML は sandbox 付きの iframe で隔離する。

全体像: 書き込みと配信の経路

書き込みはどのインスタンスに届いても Firestore への 1 トランザクションになる。配信はアプリ側の pub/sub を使わず、ペーパーを開いている各インスタンスが Firestore のリスナーで変更を受け取り、自分の WebSocket 接続に流す。

ここでいう「リスナー」は Firestore の snapshot listener を指す。Cloud Run のサーバーが Firestore に対して張る gRPC のストリーミング接続で、ブラウザとの WebSocket とは別物。ブラウザは Firestore に直接つながらない。

データモデル: ブロックの履歴がペーパーをつくる

ペーパーはブロックの並びで、並び順は fractional index（文字列キー）で決める。挿入や移動で他のブロックを書き換えない。表は table ブロックの子として table_cell を持ち、セル単位で編集・ロックできる。

エンティティ主な項目メモ
Workspace名前、ロールバインディングUI で切り替える単位
Paperタイトル、アクセス設定、作成者・更新者通し番号は持たない。更新時刻は最大 1 分間隔でだけ書く
Block親、順序キー、種類、本文、属性、版版ごとのスナップショットを versions に残す
Commit実行者（人 / AI）、メッセージ、変更一覧変更は「ブロック・元の版・新しい版・上書きした版」
BlockLock保持者（接続単位）、有効期限TTL 30 秒、ハートビートで延長

ブロックの種類: 段落、見出し（1〜3）、引用、箇条書き、番号付きリスト、ToDo、コールアウト、コード、区切り線、画像、表と表のセル。AI だけが書くもの: mermaid、svg、html。

同時編集

仕組み動き
弱いロックブロックをクリックすると WebSocket 経由でロックを取る。他の人には「◯◯が編集中」と表示され、AI はそのブロックへの書き込みを拒否される。
上書き「それでも編集する」（API では force）でロックを越えて書ける。同じブロックへの同時書き込みは後勝ち。
上書きの記録古い base_version を元に書いた場合は commit に上書きした版を残し、UI で通知する。
配信イベントは変更後の状態（ブロック全体）を運ぶ。クライアントは版を比べて反映するので、重複や順序の入れ替わりがあっても収束する。
再同期接続直後（hello 受信時）に必ず読み直す。受け手が遅れてバッファが溢れたら closing: resync を送り、再接続させる。

認証・認可

認証

  • Google OIDC（authorization code + nonce、ID トークンは JWKS で署名検証）。初回ログインで papers がユーザー ID を発行し、IdP の subject と紐付ける。別の IdP は後から足せる。
  • ログインできる人は許可ドメインと許可メールで決める（Google 利用時はどちらか必須）。システム管理者はメールで指定する。
  • ブラウザはセッション Cookie（秘密値はハッシュで保存）。変更系のリクエストには X-Requested-With: papers ヘッダを必須にして CSRF を防ぐ。
  • API と MCP は Bearer トークン（pap_<id>.<secret>）。MCP はブラウザ Cookie を受け付けない。トークンはブラウザのセッションからだけ発行できる。

認可

規則内容
ロールviewer < editor < owner。付与先はユーザー、グループ、メールドメイン、サインイン済みの全員。
ワークスペースバインディングの最大値。システム管理者は全体の owner。
ペーパーワークスペースの owner は全ペーパーの owner。作成者は editor 以上である限り owner。限定公開ペーパーはペーパー側のバインディングだけで判定し、公開ペーパーではペーパー側のバインディングでロールを上げることだけができる。
トークンread は viewer、write は editor が上限。トークンは共有設定の変更やグループ管理などの権限管理ができない。
見え方読めないものは 404、読めるが権限が足りないものは 403。存在を漏らさない。

API と MCP

  • REST /api/v1/...: ワークスペース、ペーパー、POST .../commits（複数 op をアトミックに適用）、commit 履歴（新しい順、カーソル）、ブロックの版履歴、ロック、Markdown 書き出し、検索、トークン、グループ。
  • WebSocket GET .../papers/{id}/live: lock / unlock / heartbeat を送り、block_put / block_deleted / paper_updated / lock / unlock を受け取る。
  • MCP（Streamable HTTP、stateless）: papers_guide、papers_list_workspaces、papers_list_papers、papers_search、papers_read_paper、papers_create_paper、papers_commit、papers_history、papers_block_history。
  • insert_markdown op を使うと、AI は Markdown 1 本でまとめて書ける。mermaid / svg / html のコードフェンスはリッチブロックに、GFM の表は表ブロックになる。

commit のトランザクション

Firestore のトランザクションは読み込みをすべて先に済ませる必要がある。そのため実装では書き込みをメモリに積み、読み込みにはそれを重ねて見せ、最後にまとめて書く。

read   papers/{p}                    共有ロック。書くのはタイトル変更か更新時刻が古いときだけ
read   blocks/{id}                   変更するブロック
query  blocks where ParentID == X and Order > Y order by Order limit k   挿入位置
------ ここから書き込み
set    blocks/{id}
create blocks/{id}/versions/{v}      Create なので同じ版の二重書き込みは失敗する
set    search/{p}_{id}               平文がなければ delete
delete blocks/{id}
delete search/{p}_{id}
create commits/{c}
set    papers/{p}                    必要なときだけ
set    search/{p}_title              papers/{p} を書くときだけ
  • 1 変更でブロック・版・検索エントリの 3 件を書く。Enterprise には件数の上限がなく、上限はリクエストの 10 MiB なので、1 commit は 240 ブロックまで、書く本文の合計は 3 MiB までにする（本文は版と 2 回書かれ、検索エントリが最大 8 KiB ずつ加わる）。表は 200 セルまで。
  • 同じ位置への同時挿入は同じ順序キーになりうる。並びは（順序キー、ID）で決まり、次の挿入は「順序キーが厳密に大きい次の兄弟」との間にキーを作るので壊れない。

インデックスと TTL

Enterprise は索引を自動で作らない。索引のないクエリはエラーにならず、コレクションを総なめにして遅く高くなる。そのため repository のクエリはすべて pkg/repository/firestore/indexes.go の RequiredIndexes に索引を書き、papers firestore setup が不足分と TTL を作る。クエリを足すときは索引も足す（CLAUDE.md の規約）。

コレクショングループ索引使うクエリ
tokensUserID ASCListTokens
groupsMembers array-containsListGroupsByMember
blocks(ParentID ASC, Order ASC) と (ParentID ASC, Order DESC)挿入位置、表のセル、末尾
versionsVersion DESCListBlockVersions
commitsCreatedAt DESCListCommits
searchText のテキスト索引Search

ペーパー内のブロック全件・ロック全件と ID の範囲指定は索引なしで読む。単一フィールド索引が自動で付かないので、本文で保存量が膨らむ問題もない。

papers firestore setup --firestore-project-id=PROJECT --firestore-database-id=DB --dry-run
papers firestore setup --firestore-project-id=PROJECT --firestore-database-id=DB

setup はデータベースが Enterprise であることを確かめ、索引の作成を開始して戻る（構築はサーバー側で非同期）。TTL は sessions.ExpiresAt と locks.ExpiresAt。TTL による削除は最大 24 時間ほど遅れることがあるので、アプリは常に ExpiresAt を見て有効かどうかを判定する。

検索

検索は Repository.Search(ws, query, limit) の裏に隠す。use case 層は検索エントリを受け取り、権限で絞り、1 ペーパー 1 件にまとめて抜粋を作るだけで、ペーパーやブロックを総なめにしない。

検索エントリ

  • タイトル 1 件と、平文を持つブロック 1 件ごとに 1 エントリ。HTML と SVG は文字のノードだけを取り出す（script・style・属性は捨てる）。区切り線と表のコンテナは持たない。表のセルは各セルが 1 エントリ。
  • 平文は 8 KiB で切る。大きなリッチブロックが索引の大きさと結果の転送量を押し上げないようにするため。
  • リポジトリがブロックと同じトランザクションで書く。commit が見えた時点でエントリも揃っている。版の履歴は索引しない。

Firestore での実装

  • エントリはワークスペースごとのコレクション workspaces/{ws}/search に置く。Search ステージはパイプラインの先頭にしか置けず、後ろでワークスペースを絞ると件数が欠けるので、パスで範囲を切る。
  • クエリは model.ParseSearchQuery で語に分け、語ごとに引用符で囲んで渡す。利用者が打った - や OR、field: は文字として扱われ、どのバックエンドでも「すべての語を含む」の意味になる。
  • 並びは関連度のスコア順。クエリの言語は --firestore-search-language（未指定なら Firestore が判定）。
  • 権限で隠れるペーパーがあっても件数が足りるよう、limit の 3 倍まで取ってから絞る。制限付きのペーパーが大半を占めるワークスペースでは、件数が limit を下回ることがある。

費用の目安

全社集約（検索 月 約 31 万回、現行ブロック 約 800 万件）で、検索 1 回 50〜2,000 読み取り単位として月 1〜31 ドル。エントリの書き込みと索引の維持で月 数ドル。外部の検索サービス（月 450〜680 ドル）より 1 桁以上安い。

リスクと確認すること

  • 日本語の分かち書き。 契約テスト TestSearchRepository/japanese の 4 語（障害対応、認可設定、変更履歴 確認、本番環境）が通るかを実データベースで確かめる。通らなければ、エントリに 2 文字の組を持たせる方式へ Search の実装だけ差し替える。
  • Go SDK の Search は Experimental。 サーバー側は GA（2026-10-19）だが、SDK v1.29.2 では今後 API が変わりうると明記されている。使っているのは search.go の 1 か所だけ。
  • よく出る語の検索の遅さ。 800 万件規模でスコア順に並べると遅くなりうる。Query Explain で単位数と応答時間を測る。
  • 東京リージョンでの提供と単価。 公開資料では確認できていない。

デプロイ

  • Cloud Run + 外部 HTTPS LB。--timeout=3600 で WebSocket を最大 60 分保つ。--min-instances=1 を推奨。
  • WebSocket 接続中はインスタンスに課金されるので、--concurrency は大きめにする。
  • session affinity はベストエフォート。状態はすべて Firestore にあるので、どのインスタンスにつながってもよい。
  • --base-url を https にすると Cookie に Secure が付く（Cloud Run では TLS は LB で終端される）。

規模の見積もり: 瞬間最大 300 人

想定: 同時接続 300、ペーパーは平均 100 ブロック、同時に開かれているペーパーは 30 前後、編集中の人は 2 割（60 人）。結論として、Firestore の料金と書き込み性能は問題にならない。詰まるのは サーバーから Firestore への gRPC のストリーム数 で、今の実装のままでは動かない。

ストリーム上限

Google の API は 1 本の gRPC 接続あたり同時 100 ストリームまでで、この上限は変更できない。Go の Firestore クライアントは既定で接続 1 本なので、1 インスタンスで張れるリスナーは実質 100 本まで。今の方式は WebSocket 1 本につき 3 本張るため、1 インスタンスに 34 人つながった時点で上限に達し、それ以降の人には変更が届かなくなる。

案: インスタンス内でペーパーごとにリスナーを共有する

  • インスタンス内に「ペーパーのハブ」を置く。そのペーパーを最初に開いた接続がリスナー 3 本を張り、最後の接続が閉じたら止める。
  • ハブはリスナーから受け取った最新の状態（ブロック・ロック・ペーパー本体）をメモリに持つ。後から開いた人には hello と一緒にその状態を渡すので、Firestore の読み取りが発生しない。
  • あわせて Firestore クライアントの接続プールを 4 本程度に増やす（option.WithGRPCConnectionPool）。
  • ハブは Repository.WatchPaper の上（usecase 層）に置き、DB に依存させない。インスタンス間の配信は各インスタンスのリスナーが受け持つので、複数インスタンスで動く。PostgreSQL に移っても同じハブがそのまま使え、その場合は DB 接続の数と LISTEN の本数を減らす効果になる。
  • 規約との関係: 「リクエストをまたぐ状態をメモリに持たない」原則の例外になる。ハブは変更フィードのキャッシュで、失っても接続が再同期するだけで正しさに影響しない。例外はこれだけと CLAUDE.md に明記する。

全社の情報を集約した場合の月額（東京リージョン、運用 1 年目）

前提: 社員 2,000 人、平日の利用者 1,200 人。ペーパー 10 万件 × 平均 80 ブロック（本文 約 8 GB）。編集者 400 人がそれぞれ 1 日 40 回編集し（1 日 16,000 回）、AI が取り込みで 1 日 3,000 commit × 20 ブロック（1 日 60,000 ブロック）を書く。AI への質問は 1 日 3,000 件で、1 件あたり検索 2 回とペーパー読み取り 5 回。人の検索は 1 人 1 日 5 回。検索は月 約 31 万回になる。単価は 2026-11 時点の公開価格で、割引は考えない。計算は model.py の手書きモデルで、桁を見るためのもの。

書き込みとストレージ（どちらの DB でも小さい）

  • 書き込みは月 約 710 万件（ブロック本体と版のスナップショット、commit、ロックの延長を含む）。Firestore では月 6〜13 ドル。PostgreSQL ではピークでも毎秒 20〜50 件程度で、負荷にならない。
  • 既存資料の一括取り込みは 1 回だけで約 1,600 万件の書き込み（Firestore で 14〜29 ドル）。
  • 版のスナップショットは月 約 220 万件ずつ増える。保存量は 1 年で約 60 GB、3 年で約 130 GB。Firestore で既定の単一フィールドインデックスを残したままだと、それぞれ約 240 GB、約 540 GB に膨らむ。Props・Content・Actor と版の大半のフィールドはインデックス対象から外す。

読み取り: 今のコードのままでは使えない

今のコードでは Firestore の読み取りが月 約 530 億件（1.6〜3.2 万ドル）になる。原因はほぼ検索で、検索のたびにワークスペースの全ブロックを読む。AI の検索で 295 億件、人の検索で 216 億件。ほかに、commit のたびのペーパー一覧の再読み込みが 7 億件、ホームのペーパー一覧が 5 億件ある。

次の 4 点を直すと、読み取りは月 約 1.5 億件（44〜89 ドル）に下がる。どれも DB の選択とは関係なく必要。

  • 検索を専用のインデックスに移す（Firestore なら外部の検索サービス、PostgreSQL なら pg_bigm）。
  • ペーパー一覧をページ分割し、commit 後の再読み込みをやめる。
  • MCP の read_paper でブロックを 2 回読んでいるのを 1 回にする。
  • ペーパーごとのリスナーをインスタンス内で共有する（上のハブ）。

AlloyDB の最小構成（2 vCPU / 16 GB）で足りるか

  • 編集・リアルタイム配信・履歴は十分に足りる。書き込みは毎秒数十件、ペーパーを開く読み取りも主キーと (paper_id, order) の索引で済み、現行ブロック 約 8 GB と B-tree 索引はメモリに載る。
  • 足りなくなるのは全文検索。pg_bigm の GIN 索引は本文の 2〜3 倍（16〜25 GB）になり、16 GB のメモリに載らない。日本語は「こと」「する」のようなありふれた 2 文字の組が多く、こうした語を含む検索は数百万行の再確認になって 1 回数秒かかる。AI はピーク時に毎秒数回〜10 回検索するので、2 vCPU では編集の応答まで遅くなる。
  • 意味検索を足すと、ブロック単位では埋め込みが 800 万件 × 768 次元で約 24 GB になり載らない。ペーパーの節単位（約 100 万件、約 3 GB）にまとめれば載る。
  • 単一ゾーンなので、メンテナンスやゾーン障害の間は編集が止まる。止めたくなければ高可用性構成で費用が倍になる。
  • インスタンス間の配信は LISTEN/NOTIFY を使う。通知の中身は 8,000 バイトまでなので ID だけを送る。LISTEN はインスタンスあたり 1 本にまとめるので、上のハブはどちらの DB でも必要。
  • ロックの延長は毎秒 10 件前後の UPDATE で不要な行が溜まる。ロックの表は UNLOGGED にするか、短い間隔で VACUUM させる。
  • 結論: 2 vCPU / 16 GB で足りるのは「検索を DB の外に出す」か「検索対象を絞る」場合だけ。全社の検索まで同じ DB で受けるなら、4 vCPU / 32 GB か読み取りプールの追加が要る。

この比較から言えること

  • どちらでも書き込みとストレージは誤差で、費用を決めるのは検索。
  • Firestore は DB 本体が月 100 ドル前後で済むが、検索を外部サービスに頼るとクエリ課金で 500〜800 ドルになる。検索回数が増えるほど費用が増える。
  • AlloyDB は検索込みの固定額。最小構成は Firestore より安いが性能と可用性に余裕がなく、余裕を持たせると 550〜1,300 ドルになる。
  • 次に決めるのは検索の方式（外部サービス、DB 内、自前の索引）。DB の選択はそれに従う。
  • その後の決定: Firestore Enterprise の全文検索を使う（検索）。外部サービスのクエリ課金がなくなり、Firestore 側の月額は検索込みで 100 ドル前後に収まる見込み。

Cloud Run

  • 300 接続は 1 インスタンス（--concurrency 最大 1000）にも収まるが、可用性のため最小 2 インスタンスにする。
  • デプロイ時は全接続が切れて一斉に再接続する。共有後なら、各インスタンスで開いているペーパーごとに初回スナップショット 1 回で済む。
  • 全員が同じペーパーを開く場面（全体会議など）でも、リスナーはインスタンスあたり 3 本で、配信はメモリ内で済む。
