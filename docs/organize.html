ペーパーをどう整理するか

ワークスペースの中でペーパーがすべて同じ高さに並ぶと、数百を超えたあたりで人も AI も置き場所と探し場所を見失う。階層を持つか、持つならどんな形かを比べる。

2026-11-21 起草。同日、入れ物を「フォルダ」から「ペーパーの入れ子」に改めた（フォルダは「まとめのペーパー + 子の一覧」と同じで冗長なため）。モデルと概念の続き。決めることの番号は D19 から続ける。決まったものはモデルと概念に反映済み。実装はまだしない。

追記（11-21）: モデルの D15 で、commit・リリースをまとめて「版」（人か AI が明示的に保存したペーパーの写し。システムが勝手に作ることはない）だけにした。自動保存という概念はなく、ほかは今の状態（編集中の最新版）があるだけ。これにより、この文書の D22（移動を commit に残す）・D32（MoveID）は取り下げ、D26 の「リリース」は「版」、D29 の /latest・/v/{番号} は版を指し、D30（誰でも保存できる、AI も含む）はそのまま。決まったことはすべてモデルと概念に反映済みで、そちらを正とする（この文書は検討の経緯）。

フラットだと何に困るか

置き場所や見通しは、検索と一覧の並べ替え、AI への目次で足りる。フラットで本当に困るのはまとめて扱えないことだけで、それが次の場面で表に出る。

場面フラットだと
検索・一覧の範囲を絞る「この案件の中で探す」ができない。ワークスペース全体から探すしかない。
AI に読ませる範囲「この案件の資料を全部踏まえて書いて」と言っても、どれがその資料かを AI が推測するしかない。MCP の読み取り・検索に範囲を渡せない。
片付け終わった案件の資料をまとめてアーカイブ・削除・別のワークスペースへ移す、ができない。1 件ずつになる。
書き出し案件の資料を一式で Markdown や PDF に書き出せない。
見守る「この案件で何か変わったら知らせて」の単位がない（通知を作るとき）。

もう 1 つ、まとまりごとの「まとめ」を定義しにくい。案件の概要、資料の目次、現状の結論のような、まとまり全体について書く場所がない。フラットでは「まとめ用のペーパー」を作っても、どの資料のまとめなのかが構造として表れない（入れ子なら親ペーパーの本文がまとめになる）。

さらに、正本と使い捨てが混ざる。AI は議事メモ・調査の途中経過・下書きを大量に作るので、整理された知識がその中に埋もれる。ただしこれは置き場所ではなく「ペーパーがどこまで固まったか」の問題で、階層ではなく状態で表すほうが筋が良い（D26）。

問題としない（検討済み）

  • 一部の人だけに見せる資料: ワークスペースで表す。まとまりにアクセスの範囲は持たせない。
  • 範囲ごとの書き方の決まり: 本質ではない。決まりはワークスペースの description で足りる。
  • まとまりの中の順序: 本質ではない。
  • パスで指す: URL で足りる。
  • 同じ名前の衝突: 検索結果に作成者と更新時刻を出せば足りる。

したがって必要なのは「ペーパーの集合を名前で指せること」と「その集合のまとめを持てること」で、上の場面だけなら 1 段のまとまりでも満たせる。しかし整理という観点では入れ子の構造が要る。理由は人が認知できる形がそれくらいしかないから。人は数百の並びを一度に把握できず、数個〜十数個ずつのまとまりに分け、それをさらにまとめる形でしか全体をつかめない。AI は検索と目次で平らな集合を扱えるが、人が全体を見渡して「どこに何があるか」を持つには入れ子が要る（案件の中に調査・手順・振り返りを分ける、など）。そこでペーパーを入れ子にする（D19）。深さは制限しない（D20）。まとまりの所属が 1 つに決まっている（タグのように複数ではない）ほうが、片付けと書き出しで「どれが含まれるか」が明確になる。

ワークスペースを細かく分けて代わりにする手もあるが、ワークスペースは設定ファイルで定義する（管理者の領分）ので、日々の整理には使えない。

形の候補

A. タグ

階層なし。ペーパーに複数のタグを付け、タグで絞る。

B. フォルダ

ペーパーとは別の入れ物。フォルダは入れ子にでき、ペーパーはちょうど 1 つのフォルダに入る。

C. ペーパーの入れ子

ペーパーが親を持つ。子の一覧は本文の外（本文の下やサイドバー）に出る。

F. 子ペーパーをブロックで埋め込む

Notion の方式。子ペーパーは親の本文の中の「ペーパー」ブロックとして、書いた位置に並ぶ。

D. 目次ペーパーとリンク

構造は持たず、ペーパーへのリンクを並べた「目次」のペーパーで束ねる（Wiki の方式）。

埋め込み（F）の懸念と解き方

懸念解き方（推奨）
子の置き場所が、親の本文（ブロックの版）に混ざる混ざることを受け入れる。子の追加・削除・並びの変更は親の本文の変更として親の履歴に残り、文脈の中で「いつ子が増えたか」が分かる。子の中身は親の版に入らない（ペーパーブロックは子の ID しか持たない）。
ペーパーブロックを消したら子はどうなるか子を配下ごとゴミ箱に入れる（D21）。画面は消す前に「子ペーパー n 件もゴミ箱に入ります」と確かめる。親の版を戻して（restore）ブロックが戻れば、子も一緒に戻る。
衝突の判定に巻き込まれるペーパーブロックの中身（子の ID）は変わらないので、内容の衝突は起きない。並びの変更は他のブロックと同じく後勝ち。子のタイトルは子のものを表示するだけで、ブロックには持たない。
同じ子を 2 か所に置く（コピー・貼り付け）できない。子のペーパーブロックはちょうど 1 つ。他の場所から指したいときは普通のリンク。
移動が 2 つのペーパーにまたがる元の親からペーパーブロックを消し、新しい親に足し、子の親を書き換える。これを 1 つのトランザクションで行う（commit の持ち方は D32）。
privateprivate は木の外にフラットに置く（D27）。private のペーパーはペーパーブロックを持たず、どこにも埋め込まれない。
循環（自分の子孫の下へ動かす）移動のトランザクションの中で、移動先から親を辿り、自分に行き当たらないことを確かめる。
AI が「親の本文に書くか、子にするか」で迷うpapers_guide に「親の本文はまとめ（概要・各子の紹介・現状の結論）、詳細は子に書く」と書く。子を作るのは「親の本文のこの位置にペーパーブロックを足す」操作なので、まとめの文脈と一緒に置ける。

移動で起きること

この節では、次の記号を使う。

  • P: 動かすペーパー（配下に n 件のペーパーを持つ）
  • O: P の元の親（O の本文に P のペーパーブロックがある）
  • N: P の新しい親（N の本文に P のペーパーブロックを置く）
  • X: N の本文の中で、P を置く位置の直前のブロック

例: 「手順」（O）の下の「DB 切り替え」（P）を、「インフラ」（N）の本文の「概要」の段落（X）の後へ動かす。

書き込むもの

対象変化同じトランザクションか
O の本文P のペーパーブロックを削除（ブロックの版が 1 つ増える）。O に commit同じ（3 つで 1 つ）
N の本文X の後に P のペーパーブロックを新しいブロックとして挿入（ブロックはペーパーをまたがないので、O のブロックを動かすのではない）。N に commit
PParentID を書き換え。P に move_paper の commit。3 つの commit は同じ移動の ID で結ぶ（D32）
P の配下 n 件何も書かない。配下は親（P）を指しているだけなので、P が動けば配下もそのまま付いていく—
検索エントリ変えない。祖先を持たせないので、移動で書き直す必要がない。「この配下で探す」は、検索で当たったペーパーそれぞれの親を辿って絞る（当たりは少数なので辿る量も少ない）—

受け付ける前の検査

  • P はホームではない。P は public（private は木にない。private を public にするのは「どこにもない所から N へ置く」移動）。
  • N は同じワークスペースの public のペーパーで、ゴミ箱にない。ワークスペースをまたぐ移動は写して消す別の処理（D35）。
  • 循環しない: N が P 自身でも、P の配下でもない（N から親を辿って P に行き当たらない）。
  • 動かした後の深さが安全弁（100）を超えない。配下の深さは数えないので、安全弁は「辿るときに 100 段で打ち切る」として働く。
  • N がアーカイブ済みでも置ける。アーカイブは各ペーパーの印で、配下に継がない（P はアーカイブされない）。

同時に起きたとき

同時に起きること結果
2 人が同じ P を別々の場所へ動かす後勝ち。トランザクションが P を読み書きするので、後の方は先の結果（新しい O）から改めて動かす。
A が X を Y の下へ、B が Y を X の下へ（循環になる組み合わせ）両方のトランザクションが相手を読むので、片方がやり直しになり、やり直しで循環を見つけて拒否する。
P の移動中に、誰かが O の本文で P のペーパーブロックを削除（= 配下ごとゴミ箱）先に終わった方が勝つ。移動が先なら削除は「もうない」で何も起きない。削除が先なら移動は「P はゴミ箱」で拒否。
P の移動中に、N の祖先が動くP のトランザクションは N から根までの親を読むので、そのどれかが書き換わればやり直しになり、新しい親の並びで確かめ直す。
N の本文で X が同時に削除・移動される普通の挿入と同じ規則（X がなければその直前の生きているブロックの後、なければ先頭）。
O や N の本文が同時に編集されるペーパーブロックの追加・削除は他のブロックの内容と衝突しない。並びは後勝ち。

履歴とリリース

  • O・N・P それぞれの履歴に移動が残り、移動の ID で互いに辿れる。「誰が、どこから、どこへ」が分かる。
  • O の古いリリース（v2 など）には P のペーパーブロックが含まれる。v2 を開くと P は「現在は N の下」として今の P へのリンクで出す。
  • O を古い版に戻しても、P のペーパーブロックは戻らない。P は移動した時点で O の管理から外れている（D34）。
  • P 自身のリリースは変わらない（親はリリースに含めない）。P の /v/{番号} のパンくずは今の場所を出す。

派生データと画面

  • パンくず・パスが変わる。パスは保存していないので書き換えは要らないが、人が覚えていた「場所」は変わる。URL とリンクは ID なので切れない。
  • お気に入りは ID なので残る。P が他のお気に入りの配下に入れば、サイドバーで 2 か所に見える（同じペーパー）。
  • O・N・P と、配下を開いている画面に変更フィードで届き、サイドバーとパンくずが更新される。
  • 「この配下で探す・アーカイブ・書き出す」の範囲が変わる（O の配下から外れ、N の配下に入る）。将来の「配下の変更を見守る」も同じ。
  • 公開範囲とアクセスは変わらない（同じワークスペースの中で、public のまま）。
  • 元に戻す特別な操作はない。戻すのは「元の場所へもう一度動かす」。

推奨: 子ペーパーをブロックで埋め込む（F）

入れ物の概念は作らない。子ペーパーは、親の本文の中の「ペーパー」ブロックとして存在する。親の本文がそのまま、子を紹介しながらまとめる場所になる。

画面での見え方

  • 子を作る: 本文の好きな位置で「ペーパーを足す」。その位置にペーパーブロックができ、新しい子ペーパーが開く。
  • 子を動かす: ペーパーブロックを親の本文の中でドラッグすれば並びが変わる。別の親へは「移動」で選ぶ（パスでも指せる）。
  • ペーパーを開くと: 上にパス（パンくず）と状態（v3・正本など）、次に本文。
  • 木全体は見せない。サイドバーには、ユーザーが選んだお気に入りのペーパーとその配下だけを出す（D33）。入口はワークスペースのホーム（D31）、お気に入り、検索、パンくず。

ブロックの種類に足すもの

paper
子ペーパーのブロック。属性は子の ID だけ。タイトル・状態は子のものを表示する。本文の一番上の段にだけ置ける（表のセルには置けない）。

ペーパーに足すもの

ParentID
親ペーパー。親の本文にあるペーパーブロックと常に一致する（同じトランザクションで書く）。ホームのペーパーと private のペーパーは空。
ReleaseNumber
最新のリリースの番号。0 なら下書き、1 以上なら正本（D26）。
ArchivedAt
アーカイブした時刻。空でなければアーカイブ。

子の並び順は、親の本文のブロックの並びがそのまま使われる（別に持たない）。

決まりごと

  • public のペーパーは、ホームを除いて、ちょうど 1 つの親の本文にちょうど 1 つのペーパーブロックとして置かれる。
  • 子を作る・動かすのは、親（と動かす元）のペーパーを使える人と、その代理の AI。管理者の権限は要らない。
  • 深さは制限しない（D20）。
  • 移動は後勝ち。ワークスペースをまたいでは動かせない。
  • 親のリリースはペーパーブロック（子の ID）を含むが、子の中身は含まない。子はそれぞれのリリースを持つ。

読み込み

全体の件数に左右されない形にする。

  • 子の一覧は親の本文を読めば分かる。子のタイトル・状態は、ペーパーブロックの子 ID を一括取得で 1 回読む。
  • サイドバーで枝を開くときは、その子だけを (ParentID, …) の索引で読む。
  • パンくず: 親を 1 段ずつ辿る（深さの分だけ読む）。サーバーは「ペーパー → 親」の対応を手元に覚えておき、変更フィードで更新するので、多くの場合は読み取りなしで組める（D28）。
  • 「この配下で探す」: 検索の当たりそれぞれの親を辿り、対象の配下のものだけ残す。
  • 「この配下をまとめてアーカイブ・書き出す」: 対象から子の索引で 1 段ずつ降りて集める。まれな操作なので、裏で進める処理にする。

パスで見せる・指す

  • 見せる: 祖先のタイトルをつないで security / 手順 / DB 切り替え と出す。パスは保存しないので、途中のタイトルを変えても配下は書き換えない。
  • 指す（AI・検索）: AI はパスで親を指定できる（parent_path: "手順/DB 切り替え"）。同じ親の下に同じタイトルが複数あれば、候補を返して ID で選び直してもらう。
  • URL は ID のまま（/ws/{ws}/p/{id}）。

AI からの使い方

  • papers_guide はホームの本文を返す。AI はまとめを読み、ペーパーブロックを辿って必要な枝を降りていく。
  • 子を作るのは commit の操作の 1 つ（insert の種類 paper、子のタイトルつき）。親の本文のどこに置くかを after で決める。
  • 読み取りと検索に「このペーパーの配下」の範囲を渡せる。

決めること

D19. 整理の形（決定: F 子ペーパーをブロックで埋め込む）

A（タグ）・B（フォルダ）・D（目次とリンク）・G（AI が木を作る）は却下。

案形良い点気になる点
C. ペーパーの入れ子ペーパーが ParentID を持つ。親の本文がまとめ概念が増えない。位置（親）と内容（本文）が分かれている親の本文の中で子に触れても、子の一覧とは別物になる
E. パスの名前空間ペーパーが security/手順/DB 切り替え のようなパス名を持ち、階層はパスから決まる（S3 の prefix、ファイルシステム）。同じパスのペーパーがその段のまとめ人にも AI にも読める。AI はパスを書くだけで置ける途中の段の名前を変えると配下のパスを全部書き換える。まとめのペーパーがない段は名前だけの空の段になる。URL がパスに引きずられる
F. 子ペーパーをブロックとして埋め込む子ペーパーは親の本文の中の「ペーパー」ブロックとして存在する（Notion の実際の仕組み）。並びも本文の順まとめの文章と子が同じ流れに並び、文脈の中で子を紹介できる。並び順も自然に持てる位置が内容（ブロックの版）に混ざる。ブロックを消すと子はどうなるか、衝突の判定に移動が巻き込まれる、など C で分けた問題が戻る
G. AI が木を作る（却下）人は木を作らない。AI が内容から分類の木を作って保つ—人のメンタルモデルとかけ離れる。構造は人が「どこに何があるか」を持つためのもので、人が作って人が覚えるものでなければ意味がない。AI は人が作った木の中で置き場所を選ぶだけにし、木の形を変えるのは人の操作に限る（AI が移動するのは人に頼まれたとき）。
決定: F（C の画面を見たうえでのユーザー判断）。子を本文の外に出す C は、結局「子の一覧ブロックを本文に置きたい」になり、それなら最初から埋め込むほうが自然。F で戻ってくる問題（位置が版に混ざる、ブロックの削除と子、移動）は埋め込みの懸念で解く。E の読みやすさはパスをその場で組み立てて得る。

D20. 深さ（決定）

制限しない。実装上の安全弁として 100 段で止めるが、壊れたデータや暴走した AI から守るためのもので、仕様の上限ではない。パンくずは深いときに途中を省略する。

D21. 子のあるペーパーの削除（決定: 子ごとゴミ箱へ）

子のあるペーパーを削除すると、配下全体がゴミ箱に入り、戻すときも一緒に戻る。モデルの D4-A（ペーパーのゴミ箱、30 日後に本当に消す）を前提にする。

追記: 削除（ゴミ箱へ・戻す・完全に消す）は作成者本人だけ。配下ごとの削除は、配下がすべて本人のペーパーのときだけ。他の人はアーカイブする（モデルの D18）。

  • 一緒に消えたものを覚える: 配下の各ペーパーに DeletedAt と DeletedWith（削除を始めたペーパーの ID）を付ける。戻すときは DeletedWith が同じものだけを戻す。それより前に個別に消されていた子は戻さない。
  • 大きな配下: 1 トランザクションに収まらなければ分けて書く。配下から先に印を付け、最後に削除を始めたペーパーに付ける。途中で止まっても、同じ削除をやり直せば続きから終わる（同じ印を付けるだけなので何度やっても同じ）。
  • 子だけを戻す: 親がまだゴミ箱にある子を戻すと、ゴミ箱にない一番近い祖先の下（なければ直下）に戻る。
  • 見え方: 一覧・検索・読み取りは DeletedAt のあるペーパーを除く。検索エントリは消さず、検索の後で除く（大きな配下で検索エントリを一斉に書き直さないため）。
  • 本当に消す: 30 日たったら、DeletedWith ごとに配下のブロック・版・commit・検索エントリまで消す。

D22. ペーパーの移動を履歴に残す（決定）

  • 移動は動かしたペーパーの commit として残す。操作 move_paper、変更は「元の親 → 新しい親」。誰が（AI なら誰の代理で）動かしたかは、他の commit と同じく書き手として残る。
  • 配下のペーパーには何も書かないので、配下には commit を作らない。配下の履歴では、動いたのは起点の commit で分かる。
  • 同じ扱いで、配下ごとの削除と復元（D21）も起点のペーパーの commit に残す。
  • 位置は内容ではないので、移動は衝突の対象にしない（後勝ち）。

D23（フォルダを誰が作れるか）・D24（直下に置けるか）・D25（フォルダのまとめ）は、フォルダをやめたので取り下げた。子を作れる人は「親を使える人」、直下には置ける、まとめは親の本文。

D26. 正本と使い捨てを分ける（方向は決定: リリースで版を重ねる）

正本という状態を持つなら、ちゃんと版管理をする。正本になったときが v1 で、以後はユーザーが指定したときに v2、v3 … と版を重ねる。ブロックの版（編集のたびに自動で増える）とは別のもので、紛らわしいのでリリースと呼ぶ（表示は v1, v2 …）。

状態

状態条件一覧・検索（既定）
下書きリリースがない（ReleaseNumber = 0）出さない（切り替えで出す）
正本リリースが 1 つ以上ある出す
アーカイブArchivedAt がある（リリースの有無によらない）出さない（切り替えで出す）

正本から下書きには戻らない（リリースは取り消さない）。要らなくなったらアーカイブする。アーカイブは配下ごとの片付けにも使う。

リリースが持つもの

Number
1 から欠番なし。
Note
この版で何が変わったか（任意。AI に下書きさせてもよい）。
Title / Blocks
その時点のタイトルと、全ブロックの (ブロック ID, ブロックの版, 位置) の列。ブロックの版は不変なので、本文は写さず版を指すだけでよい。
CommitID
リリースした時点の最後の commit。
CreatedBy / CreatedAt
リリースした人と時刻。

できること

  • 任意の 2 つのリリースの差分（ブロックの版を比べる）。リリース以後の変更（未リリースの変更）の差分。
  • ペーパーをあるリリースの状態に戻す: 各ブロックをその版へ復元する commit を作る（履歴は書き換えない）。
  • リリースを指す URL（…/p/{ID}/v/2、D29）。参照先として安定する。

まだ決めること

  • 読む人に何を見せるか（D29）。
  • 誰がリリースできるか（D30）。

D29. URL と、それぞれが見せるもの（決定）

URL見せるもの編集
/ws/{ws}/p/{id}（末尾の / も同じ）今の状態。リアルタイムで更新される編集中の最新版できる
/ws/{ws}/p/{id}/latest最新のリリースを指す。リリースが進めば次の版を指すできない（「編集する」で何も付けない URL へ）
/ws/{ws}/p/{id}/v/{番号}リリース vN。中身が変わらないできない
/ws/{ws}そのワークスペースのホーム（D31）の今の状態できる
/最後に開いたワークスペースのホーム。初めてなら使えるワークスペースの一覧—

/edit は設けない（何も付けない URL がその役）。使い分けは、一緒に書く・今を見るなら何も付けない URL、確定した内容を指すなら /latest、その文面そのものを指すなら /v/{番号}。

  • 下書き（リリースがない）の /latest: 「まだリリースがありません」と出し、何も付けない URL へ案内する。
  • 何も付けない URL での表示: リリースがあれば「v3 からの変更 n 件（うち AI n 件）」を出し、差分と /latest に移れるようにする。これが書く人へのリリースの促しにもなる。
  • 本文中のリンク・ペーパーブロック・サイドバー・検索結果: 何も付けない URL へ。リンクを書くときに /latest や /v/{番号} を選ぶこともできる。
  • 検索: 今の状態から探す。
  • AI の読み取り（MCP）: 既定は今の状態。at（current / latest / 番号）で指定もできる。AI が回答の根拠として示すのは /v/{番号}（後で中身が変わらない）。

D30. 誰がリリースできるか（決定: 誰でも）

リリースとは、ユーザーが「ここで版を重ねる」と指定したときに、そのペーパーのその時点の中身（タイトルと全ブロック）を v1、v2 … として固定したもの。最初のリリース（v1）を作ったときに、ペーパーは下書きから正本になる（D26）。編集のたびに自動で増える「ブロックの版」とは別物なので、名前を分けている。

決定: そのペーパーを使える人なら誰でもリリースできる（ロールを持たないので、他と同じ扱い）。

  • リリースには、した書き手（人か AI か、AI なら誰の代理か）が残り、画面の版の一覧と何も付けない URL の表示に出る（「v3 · Alice」「v4 · Claude（Alice の代理）」）。
  • リリースも commit と同じく取り消さない。気に入らなければ、前のリリースの状態に戻してから次のリリースを作る。

D27. private は木の外にフラットに置く（決定）

Notion の「プライベート」欄と同じく、private のペーパーは共有の木に入れず、ワークスペースの中の自分だけの平らな一覧に置く。

  • private のペーパーは親も子も持たない（ParentID は空）。共有の木にあるのは public のペーパーだけ。
  • public にすることは、木のどこかに置くことと同じ。親を選んで（または直下に）置く。1 つの commit に「公開範囲の変更」と「移動」の両方が残る。
  • private にするのは、子のない public のペーパーだけ。木から外れて自分の一覧に移る。子のあるペーパーは、先に子を動かす。
  • これで木の中に「見えない親」も「見えない子」も生じない。配下ごとの削除（D21）に他の人の private が含まれることもなくなる。

D28. 木の読み方（決定: 親だけを持つ）

移動で数千〜数万のペーパーが動くこと（上の段の大きな枝の付け替え）を想定する。

  • A. 各ペーパーに祖先の ID 列を持つ: パンくずも配下の範囲も 1 回で読める。代わりに、枝を動かすと配下の全ペーパーを書き直す。数万件なら数分かかる裏の処理になり、その間は配下の移動・削除を止め、パンくずもずれる。
  • B. 親だけを持つ: 移動は元の親・新しい親・動かすペーパーの 3 件を書くだけで、配下が何件でも一瞬で終わる。代わりに、パンくずは深さの分だけ親を辿り、配下の範囲は 1 段ずつ降りる。
決定: B。以前は「移動は少ない」としか見ておらず、件数を見積もっていなかった。数万件が動くなら、A は移動のたびに大きな裏の処理と、途中の不整合の扱い（止める・再開する）を抱える。B なら移動はいつも 3 件で、ロックの要らない今の設計とも揃う。B の読み取りの費用は次のように抑える。
  • パンくずと循環の検査: サーバーが「ペーパー → 親」の対応を手元に覚え、変更フィードで更新する。ずれていても親が正本なので、トランザクションの中では読み直して確かめる。
  • 「この配下で探す」: 当たりの親を辿って絞る。当たりは上位の数十件なので辿る量は小さい。
  • 配下をまとめて扱う（アーカイブ・書き出し）: まれな操作なので、子の索引で 1 段ずつ降りる裏の処理にする。

D31. ワークスペースには必ずホームのペーパーを作る（決定）

ワークスペースごとに根のペーパー（ホーム）を 1 つ持つ。いちばん上の段のペーパーはホームの本文に埋め込まれる。「ホーム以外の public のペーパーはちょうど 1 つの親の本文にある」という 1 つの決まりで木全体を説明できる。

  • 作るとき: ワークスペースは設定ファイルで定義するので、起動時に設定のワークスペースそれぞれについて、ホームがなければ作る（何度起動しても 1 つだけ。トランザクションで「なければ作る」）。最初のタイトルは設定の name、本文は空。
  • どれがホームか: 保存先にワークスペースの記録（workspaces/{ws}）を置き、HomePaperID を持たせる。ホームも ID は普通のペーパーと同じ形式。
  • できること: 本文とタイトルの編集、リリース、ペーパーブロックで子を置く、は普通のペーパーと同じ。
  • できないこと: 削除（ゴミ箱を含む）、移動、private にすること。ホームの中のペーパーブロックを消すのは子の削除（配下ごとゴミ箱）で、ホーム自体は残る。
  • 役割の分け方: 設定の description は「AI への決まりごと」（デプロイで変える）。ホームの本文は「人と AI が読むワークスペースのまとめと入口」（誰でも書ける）。
  • 設定からワークスペースを外しても、ホームを含むデータは残る（モデルの D13）。

D32. 移動の commit は 3 つのペーパーそれぞれに作り、移動の ID で結ぶ（決定）

移動は、元の親（ブロックを消す）・新しい親（ブロックを足す）・動かすペーパー（親が変わる）の 3 つにまたがる。commit はペーパーに属するという今のモデルを崩さず、それぞれのペーパーに commit を作る。

  • 3 つの commit は同じ MoveID を持ち、どれからでも他の 2 つに辿れる。書き手・時刻・メッセージは 3 つとも同じ。
  • 3 つは 1 つのトランザクションで書くので、どれかだけが残ることはない。
  • 同じ扱いを、private から public にする（親に置く）・public から private にする（親から外す）にも使う。こちらは 2 つ（親と本人）。

D33. サイドバーはお気に入りとその配下、最近開いたもの（決定）

木全体は出さない。

  • お気に入り（ピン）: ユーザーが選んだペーパー。ユーザーごと・ワークスペースごとで、並びも本人が決める。モデルに Pin（ユーザー・ワークスペース・ペーパー・並び順キー）を足す。他の人には影響しない（ロールも要らない）。
  • 配下: ピンの下は、開いた段だけ子の索引で読む。
  • 最近開いたもの: 最近開いたペーパーを数件（例: 10）自動で出す。端末をまたいで同じにするため保存先に持つ（ユーザーとワークスペースごとに 1 件の記録を、開くたびに更新）。
  • 入口: ホーム（D31）は常に出す。新しく入った人の最初の入口になる。
  • ピンしたペーパーがゴミ箱に入ったら出さない（戻れば出る）。移動してもピンは ID なので残る。自分の private もピンできる。

D34. 古い版を戻したとき、よそへ移った子は戻さない（決定）

例: ペーパー「手順」の本文には、10 月 1 日の時点で子ペーパー「DB 切り替え」のペーパーブロックがあった。その後、誰かが「DB 切り替え」を別のペーパー「インフラ」の下へ移動した（「手順」の本文からはブロックが消え、「インフラ」の本文に足された）。いま「手順」を 10 月 1 日の版に戻すと、「DB 切り替え」のペーパーブロックも戻ろうとするが、「DB 切り替え」は今「インフラ」の下にある。そのまま戻すと、1 つのペーパーが 2 か所に置かれてしまう。

移動した子は、移動した時点で元の親の管理から外れている。「手順」を戻すのは「手順」自身の中身を 10 月 1 日の状態にすることで、他のペーパーの置き場所を変えることではない。

  • 「手順」の本文・タイトルは 10 月 1 日の状態に戻す。よそへ移った子のペーパーブロックだけは戻さない（その位置には何も置かない）。
  • 確認なしで戻す。結果には「よそへ移った子 1 件（「DB 切り替え」、今は「インフラ」の下）は戻していません」と添える。AI や API からの復元でも同じ結果を返す。
  • ゴミ箱に入った子は別: 「手順」の本文でブロックを消して配下ごとゴミ箱に入れた子は、まだ「手順」の管理下にある。版を戻してブロックが戻れば、子もゴミ箱から戻る（D21）。ただし 30 日を過ぎて本当に消えた子は戻らない。
  • 古い版を見るとき（/v/{番号} や履歴）は、当時あった子の項目をそのまま出し、「現在は「インフラ」の下」と添えて今の場所へリンクする。

D35. ワークスペースをまたぐ移動は「写して消す」（決定）

画面と API には「移動」として出すが、中身は、移動先のワークスペースへの写しと、元の配下ごとの削除（D21）。ワークスペースは保存先のパスも分かれているので、同じ ID のまま動かさない。

流れ

  1. 移動する人が移動先のワークスペースを使えるか、移動先で親にするペーパーが置ける状態か（public で、ゴミ箱にない）を確かめる。
  2. P と配下を、新しい ID で移動先に写す（裏の処理。配下が多ければ時間がかかるので進み具合を出す）。写している間、元は読めるが書けない。
  3. 写し終えたら、元のペーパーを配下ごとゴミ箱へ入れる（30 日は戻せる）。
  4. 元の ID から新しい場所への転送の記録を残す。

何を写すか

もの扱い
タイトル・本文（今の状態）写す。
最新のリリース元にリリースがあれば、その内容を写しの v1 にする。今の状態とリリースの差（未リリースの変更）もそのまま保つ。リリースのない元は下書きのまま。
古いリリース・ブロックの版・commit写さない。写しの最初の commit に「{元のワークスペース}/{元の ID} から移動、移動した人」を残す。元の履歴はゴミ箱にある間（30 日）だけ見られる。
配下の中のペーパーブロック・リンク配下の中を指すものは新しい ID に付け替える。配下の外を指すリンクはそのまま（元のワークスペースのペーパーを指し続ける）。
privateprivate のペーパーは、移動先での自分の private の一覧へ写す。
検索エントリ移動先で作り直す。元のものは削除と一緒に除かれる。

移した後

  • 古い URL: 転送の記録を見て新しい場所へ転送する。移動先のワークスペースを使えない人には、今までどおり「存在しない」（404）を返し、移動先を漏らさない。転送の記録は消さない（小さいので）。
  • お気に入り: 古い ID のピンは、転送の記録を見て新しい ID に付け替える。
  • 見える人が変わる: 移動先のワークスペースの規則で決まる。画面は移動の確認で「見える人が変わります」と出す。

D36（大きな配下の移動）は、D28 を B（親だけを持つ）にすれば配下の書き直しがなくなるので取り下げた。
