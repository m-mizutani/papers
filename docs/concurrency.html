Concurrent editing: versions instead of locks

Decided and implemented 2026-11-21. The gist was also carried into "Concurrent editing" in docs/design.html.

2026-11-22: superseded. Dropping locks, refusing a conflict once and overwriting with force still hold, but per-block versions (base_version) and commits are gone. Conflicts are now judged by each block's internal revision Rev, and history consists only of versions saved on purpose. The source of truth is Model and concepts.

Decisions

  • Drop block locks11-21Nothing blocks writes; in effect the last writer wins. Lock records, renewals, the TTL and the WebSocket lock operations all go.
  • Make versioning strict instead11-21For every change it must be possible to tell who wrote what, based on which version, and anything that disappeared must be recoverable from history.
  • Refuse a conflict once, then allow forcing it (option B)11-21Stop at the moment of saving, show both contents, and overwrite with force only when the writer chooses to. The same for AI: it gets an error with the current contents and writes again.

Versioning rules

Whatever is done about conflicts, this comes first.

1. Every op on an existing block carries its base version

update, delete and restore require base_version (400 without it). move never conflicts and needs none. The UI sends the version at the moment editing started; sending the latest one received just before saving would miss changes by others that arrived during the edit. papers_guide tells AI to send the version it read.

2. Only conflicts of contents count

Version numbers also go up on moves, so comparing numbers is not enough. When base_version is older than the current one, its snapshot is compared with the current block; a change in type, text or properties is a conflict. A change only in order or parent is not.

My opWhat the other didResult
updatechanged the textconflict
updateonly moved itno conflict (my text, their position)
updatedeleted itconflict (they wanted it gone)
deletechanged the textconflict (their fresh change would vanish)
movechanged the text or moved itno conflict (order is last-writer-wins and harmless)

The comparison reads versions/{base} once, and only when the base is old, so ordinary reads do not grow.

3. An overwrite records whose what it replaced

Change records the overwritten version and its writer (the snapshot's UpdatedBy), so history can say "B overwrote A's v5".

4. Add an op to go back

{"op":"restore","block_id":"…","version":5,"base_version":7}

It makes a new version v8 with v5's type, text and properties (history is not rewritten). A deleted block comes back with the same ID near its last position. In the UI, each version in the history panel gets "Go back to this version".

5. Recording deletions (not done)

Appending a "deleted" version on deletion was left out: who deleted when is in the commit, and a deleted block can come back from its last version with restore. Add it if it becomes necessary.

Handling conflicts (decided: option B)

A and B both see v3. B saves first, making v4. What happens when A saves based on v3?

Option A: warn only (plain last writer wins)Option B: refuse and let the writer choose (refuse by default, last writer wins on request)
On savingAlways goes through; afterwards "You overwrote B's change" is shownStops with 409 and shows B's v4 next to one's own. Choose "Save mine", "Keep theirs" or "Keep editing"
For AIGoes through; the result notes the overwrite (an AI that does not read it never notices)An error with the current contents comes back. The AI rereads and writes again, or overwrites with force
Lost contentsIn history; getting them back needs someone to notice and restoreNothing is lost unless overwriting is chosen
EffortNone when saving; large when the overwrite is noticed lateOne choice, only on a conflict, which is rare
AI writing a lotNothing stops AI from overwriting a block a person is fixingThe AI stops, takes in the person's change and writes again
ImplementationA record added to today's behaviourA conflict error in the use cases, a comparison dialog in the UI, force explained in MCP
Adopted: option B (refuse by default, last writer wins on request)

Without locks, the only moment a person can learn of a conflict is when saving. Stopping there loses nothing, and it stops only when two people changed the same block at the same time, so it costs little. For AI, the main writer, stopping on an error and rereading is natural too. Last-writer-wins remains available with force, and every chosen overwrite is recorded.

While editing

  • A change by someone else to the block being edited does not replace what is being typed. "B updated this block" shows above it, and saving enters the flow above.
  • "Keep editing" keeps the draft and moves its base to the other's latest version; the next save goes through as usual.
  • If someone deletes the block being edited, the draft stays at the top of the page with "Restore and save mine" (restore and update in one commit) or "Discard mine".
  • If nothing was typed, saving sends nothing even when someone else updated the block (no conflict).
  • Blocks not being edited take incoming changes as they are (as before).
  • Showing who is editing where goes away. If needed, it comes back later as a separate mechanism that never blocks writes (presence).
  • Saving happens on leaving the block, Enter or Esc. Periodic saving to shorten the conflict window is not there yet (open question).

MCPThe meaning of force changed from "ignore others' locks" to "overwrite despite a conflict"

Renewing a lock was one write every 10 seconds per person editing. With it gone, most of the peak write load disappears.

Open questions

  1. Periodic saving while editing: the longer an edit, the likelier a conflict. Decide from use whether to save after a few seconds of pause.
  2. Telling the overwritten person: is history enough? Showing "your change was overwritten" when the paper opens needs a place for per-person notices.
  3. Tables: a cell is a block under the same rules. But deleting or shrinking a table removes cells someone just changed without a conflict check (their versions stay in history), and a deleted table cannot be restored.
  4. Titles: have no version. To follow the same rules, the paper itself would need versions.
